# Codex 多 Agent 协作规则

## 1. 目的

本规则用于 DentAll 项目每天根据实际进度和任务风险动态选择 Codex Agent。项目不维持固定数量的常驻 Agent；主 Agent 始终负责项目上下文、范围控制和最终交付，专项 Agent 仅在能够提供独立价值时按需启动。

多 Agent 审查用于降低遗漏和常见缺陷风险，不能替代专业渗透测试、支付服务商验收、真实设备测试或有资质人员的最终审核。

## 2. 每日输入与主 Agent 职责

用户每天至少提供以下信息；允许自然语言表达，不要求严格套用模板：

- 当前计划日，例如 `D12 / W2`。
- 已完成、正在进行和计划处理的内容。
- 阻塞、异常、需求变化或已知风险。
- 有代码改动时，说明涉及页面、功能或文件；信息不足时由主 Agent检查工作区确认。

主 Agent收到进度后必须：

1. 对照 `DentAll商城项目总计划-单休版.md` 和 `project-docs/PROJECT_STATE.md` 判断计划偏差。
2. 将当天工作分为低、中、高、交易关键风险，不以工作量大小代替风险判断。
3. 说明本次准备使用哪些 Agent、各自职责以及不启动其他 Agent的原因。
4. 先由主 Agent完成范围梳理和实施，再让未参与原实现的专项 Agent独立审查。
5. 汇总审查意见、修复、复测和未验证项；专项 Agent的结论不能直接替代主 Agent验收。

若当前运行环境没有可用的多 Agent 调度能力，主 Agent必须明确说明，并使用相互隔离的“实现检查”和“独立复核”两轮流程作为降级方案，不得把同一轮自检表述为独立 Agent Review。

## 3. Agent 角色

| 角色 | 职责 | 默认输入 | 输出 |
|---|---|---|---|
| 主 Agent | 读取项目事实、拆解范围、实施、整合意见、复测和更新记录 | 计划、状态、目标目录、现有实现 | 可验证改动和最终交付报告 |
| 项目/需求 Agent | 检查需求、依赖、字段、URL、数据模型和范围变化 | 原始需求、总计划、数据与架构文档 | 歧义、依赖、验收标准和范围影响 |
| 设计还原 Agent | 对照效果图检查结构、组件、断点、状态和可访问性 | 设计基线、截图、页面和样式差异 | 按严重度排列的视觉与交互差异 |
| Code Review Agent | 独立检查变更的正确性、兼容性、可维护性和回归风险 | 原始需求、验收标准、`git diff`、相关文件和测试证据 | P0～P3问题；无问题时明确说明剩余风险 |
| 安全 Agent | 检查权限、nonce、输入输出、越权、敏感数据、上传、SQL、REST/AJAX和交易边界 | 威胁面、代码差异、入口、数据流和运行配置 | 漏洞、利用条件、影响、修复建议和未覆盖项 |
| 测试 Agent | 从验收标准设计或执行正常、空、错误、边界及回归测试 | 验收标准、实现、环境和代表数据 | 测试结果、证据、缺陷与未验证项 |

专项 Agent不得擅自扩大需求、安装插件、修改生产数据、启用真实支付、切换 DNS 或提交其职责之外的修改。

## 4. 风险分级与启动规则

### 低风险

包括纯文案、文档、已冻结结构中的小型静态样式和不改变行为的资源调整。

- 默认：主 Agent实施并自检。
- 出现响应式、可访问性或跨页面影响时升级为中风险。

### 中风险

包括主题组件、模板、查询展示、筛选交互、普通表单前端、响应式页面和 WooCommerce 展示层改动。

- 必须：主 Agent + Code Review Agent。
- 涉及效果图：增加设计还原 Agent。
- 涉及多个状态或回归面：增加测试 Agent。

### 高风险

包括后台保存、角色权限、nonce、REST/AJAX、文件上传、客户数据、自定义 SQL、缓存会话、邮件发送和数据结构变更。

- 必须：主 Agent + Code Review Agent + 安全 Agent。
- 必须由测试 Agent覆盖失败、越权、重复请求和边界状态，或由主 Agent执行同等独立测试并保留证据。

### 交易关键风险

包括价格、税费、优惠券、库存、购物车、结账、支付回调、订单、退款、物流、数据库迁移和生产部署。

- 必须：主 Agent + Code Review Agent + 安全 Agent + 测试 Agent。
- P0/P1必须为零；金额、库存、订单状态、重复回调、失败恢复和回滚均需验证。
- 未经明确授权，只能使用 Local 或受保护的 Staging、支付沙盒和测试数据。

无论当前处于哪个计划日，只要任务触发更高风险条件，就按更高等级执行。

## 5. 按项目阶段的默认侧重

| 阶段 | 默认专项 Agent |
|---|---|
| D1～D6 环境、Staging与试录 | 项目/需求；涉及账号、Staging或配置时增加安全与测试 |
| D7～D25 数据模型与编辑流程 | 项目/需求；字段保存、权限和上传增加 Review、安全与测试 |
| D26～D42 全局组件与首页 | 设计还原 + Code Review；四端页面增加测试 |
| D43～D66 列表、筛选与详情 | Code Review + 测试；查询、URL和文件权限按需增加安全 |
| D67～D90 购物、结账、账户与表单 | Code Review + 安全 + 测试；视觉页面按需增加设计还原 |
| D91～D108 SEO、性能、缓存与安全 | 对应领域审查 + Code Review + 测试；权限和缓存会话增加安全 |
| D109～D120 回归、部署与交付 | 测试 + Code Review；交易、生产配置和部署增加安全 |

阶段表只提供默认侧重，不取代风险分级。

## 6. 独立 Review 规则

- Review Agent不得参与被审查代码的首次实现。
- Review输入只包含原始需求、验收标准、相关项目规则、变更差异和测试证据，不预先灌输“实现正确”的结论。
- Review优先寻找实际缺陷，不要求为了输出数量制造意见。
- 问题必须注明文件和位置、触发条件、影响和建议严重度。
- 严重度定义：P0为安全漏洞、数据丢失、错误扣款或生产不可用；P1为核心流程阻塞、越权、金额/库存/订单错误；P2为普通功能、兼容性或明显响应式问题；P3为低风险维护性或优化建议。
- P0/P1未关闭时不得标记 Done；P2如延期，必须记录负责人、计划和接受理由。

## 7. 每日 Agent 决策记录

每天在 `project-docs/PROJECT_STATE.md` 或 Obsidian 日报中记录：

| 项目 | 内容 |
|---|---|
| 当前日/任务 | Dxx、计划项和实际处理范围 |
| 风险等级 | 低 / 中 / 高 / 交易关键及理由 |
| 启动 Agent | 角色、职责和启动原因 |
| 未启动 Agent | 不需要或暂不具备条件的原因 |
| Review结果 | P0/P1/P2/P3数量和处置 |
| 验证证据 | 命令、页面、设备、账号、测试数据或截图 |
| 剩余风险 | 未验证项、阻塞和下一步 |

## 8. 完成门槛

- 代码或配置已经落地，且未超出授权范围。
- 所需专项 Agent已经完成独立检查，或明确记录调度不可用及降级复核方式。
- P0/P1为零；延期P2已记录。
- 已按风险执行测试并保留证据。
- 已说明对数据、URL、SEO、缓存、支付、物流和部署的影响。
- 主 Agent已更新项目状态；只有文档讨论且没有实际进度变化时可不更新。
