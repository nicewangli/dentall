# 商品与内容数据字典

## 字段选择规则

1. WooCommerce原生字段能表达的，不增加ACF。
2. 用户需要筛选的规格，使用全局商品属性。
3. 影响价格、SKU或库存的选择，使用商品变体。
4. 只用于结构化展示且原生字段不足的内容，才使用ACF。
5. 普通介绍放详细描述；简要卖点放简短描述。

## 数据来源与TEST规则

- 商品数据应标记为`已确认`、`来源值待确认`、`TEST`或`缺失`；只有`已确认`可以作为正式发布数据。
- 仓库分类、内部编号和内部单价只能作为建模输入，不能自动转成网站分类、公开SKU或正式USD售价。
- 未确认的价格、库存、重量、尺寸和变体组合可用TEST数据验证流程，但商品名称、SKU及相关记录必须包含明确的`TEST`标识。
- TEST数据仅限Local或受保护、`noindex`且未启用真实支付的Staging；可作为明确登记的回归夹具保留，但D25开放批量录入前必须复核并决定继续保留、归档、删除或替换，不能混入正式内容。
- 医疗/合规事实、认证结论和素材公开授权不得使用推测或TEST值代替业务确认。
- D18冻结商品模型和编辑流程候选，不代表全部正式商品资料完成；约970条仓库物料的全量清洗与录入不属于W2～W3。

## 商品类型与销售模式v1候选

第一版以前台设计稿中的标准电商闭环为基线，具有标准价格的可购买商品是开发核心；少量定制商品默认只作展示，询价仅在出现真实业务需求后条件启用。商品名称中出现“套装”“单支”“包装”或“Custom”不能直接决定WooCommerce商品类型；必须根据可售单位、顾客选择、SKU、价格和库存职责判断。

| 业务路径 | WooCommerce底层 | 判断条件 | 第一版定位 |
|---|---|---|---|
| 标准简单商品 | Simple Product | 一个可售单位；顾客不需要选择会改变SKU、价格、库存、图片或可购买性的规格 | 主要路径 |
| 标准可变商品 | Variable Product＋Variations | 同一基础商品下存在有限、合法且互斥的购买选项；具体可售组合独立承担SKU、价格或库存 | 主要路径 |
| 定制展示商品 | Product＋显式展示模式 | 用于展示定制能力、参考价格范围和服务范围，通过Contact Us接收联系，不直接销售 | 少量辅助路径 |
| 定制询价商品 | Product＋显式询价模式 | 业务明确要求客户提交规格并由人员报价 | 条件需求，当前不实施 |

### 商品类型判断顺序

1. 先确认顾客最终购买的独立订单行是什么。
2. 若不需要选择交易规格，使用Simple Product；只展示的规格不生成Variation。
3. 若顾客必须从同一商品的有限选项中选择一个合法组合，且选择会改变SKU、价格、库存、图片或可购买性，使用Variable Product。
4. 若各对象可以分别加入购物车、分别选择数量或分别管理SKU、价格和库存，应建立独立Product，不使用Variation表示多个可同时购买的对象。
5. 若组合可以任意多选、依赖共享部件库存或无法预先确定价格，不用标准Variation伪造；当前优先作为展示内容，只有真实业务要求时才转询价或另行评估Bundle/Composite能力。

### 套装、单支与包装数量边界

- 固定整套且只按整套销售时，整套使用Simple Product；不单卖的组件只作为内容或参数展示。
- 整套和单支均可分别销售时，分别建立独立Product；可使用关联商品连接，不因名称相近就建成Variation。
- 顾客自由选择多个单支组成套装时，不使用Variation；这属于Bundle/Composite或询价场景，需另行评估范围、库存联动和插件成本。
- `Package Quantity`表示一个销售包装内含多少件；购物车数量表示购买多少个包装；库存数量表示剩余多少个可售包装，三者不得混用。
- 只有多个包装规格分别拥有真实SKU、价格或库存时，`Package Quantity`才进入Variation；固定包装数量只作为属性或说明。
- 若套装由共享部件在下单后组装，普通Simple Product库存不能准确表示部件联动，未确认实现前不得宣称库存自动准确。

### 展示模式与条件询价边界

- 定制展示和询价都不是WooCommerce原生商品类型。未来实现时使用显式销售模式字段区分`standard`、`display_only`与预留的`inquiry`，候选键为`dentall_sales_mode`；默认值为`standard`。
- `standard`商品必须具备有效的正式价格才能发布；价格留空应视为资料缺失，不能自动解释为询价。
- `display_only`商品用于展示定制能力和经业务确认的参考价格范围，不填写WooCommerce成交价格，不显示普通库存、数量、加购或立即购买，也不进入结账、库存扣减和购买事件。
- 定制展示商品使用`estimated_price_min`和`estimated_price_max`两个非交易展示字段；均为USD数值，必须大于0且最低值不高于最高值，输出时使用WooCommerce金额格式API并标注`Estimated price`或等价文案。
- 参考价格范围不等于报价、Offer或可结账金额，不进入Regular price、Sale price、Variation价格、购物车、订单金额或商品Offer Schema；未确认范围时宁可不显示，也不得使用推测值。
- 展示购买区提供`Contact Us About This Product`入口，复用`/contact-us/`表单并携带Product ID；服务端根据有效Product ID读取商品名称、URL和参考范围，不信任URL传入的名称或价格。
- Contact表单向用户明确显示当前咨询商品，并随提交保存商品ID、商品名称和来源`custom_product`；表单安全、存储、邮件和失败状态沿用D89统一联系流程，不创建独立询价系统。
- `inquiry`仅在出现真实第一版询价商品和处理负责人后启用；启用时不填写虚假价格、不进入普通购物车和库存扣减，前台使用独立询价入口。
- 标准现货版和定制版同时存在时，优先拆为两个商品，避免一个购买组件同时承担直接结账和询价流程。
- 客户输入文字、Logo、文件或任意组合不属于普通Variation。价格和生产条件可预先确定时再评估Product Add-ons；当前不开发任意组合购买器。
- 展示模式会控制购买行为，若D12代表原型证明有必要，应由`dentall-core`注册、校验和授权；不使用分类、标签、描述文本或仅凭空价格代替。
- 定制展示商品继续使用同一个WooCommerce Product详情页，不另建重复Page或商品CPT；购买区根据显式销售模式显示普通购买控件或展示状态。
- 第一版暂不建设询价表单、后台询价记录、Quote Basket、人工报价转订单或询价事件；只有业务提供真实询价商品、处理人员和验收路径后，CR-004才重新进入实施。

### 设计稿约束

- 当前最终商品列表和详情设计以固定价格、库存状态、数量、`Add to Cart`、`Buy Now`及有限规格选择为主，支持Simple和Variable商品作为第一版主要模型。
- 设计稿中的`Custom Full Denture Set`仍以固定价格商品展示，不能仅凭`Custom`名称推定为询价商品。
- 当前没有定制展示商品详情状态的正式设计，后续只需补充无普通价格、库存和加购的展示购买区，以及适用时的`Contact Us`入口和四端状态。
- D12优先建立一个Simple和一个Variable TEST原型；只有展示型定制商品确认需要单独字段时，才增加最小Display Only原型。Inquiry原型当前不创建。

## 价格规则v1候选

### 标准简单商品

- `standard` Simple Product发布前必须具有业务确认的正数Regular price；空值表示资料缺失，不能自动解释为免费、展示或询价。
- WooCommerce技术上可让`0`成为可购买价格，但DentAll第一版默认不使用`0`；只有业务明确批准免费样品及其库存、物流和促销口径后才允许。
- Sale price为可选字段，必须小于Regular price。限时促销使用WooCommerce原生开始与结束日期，不在商品名称、SKU、Slug或描述中维护另一套价格状态。
- 促销结束后恢复Regular price；开放式促销只有在业务明确要求长期促销时使用，避免忘记结束日期。

### 标准可变商品

- Variable父商品负责组织属性与Variations，不保存或硬编码真实成交价；前台父级价格由当前可售Variations派生。
- 每个启用且可购买的Variation必须具有自己的正数Regular price；Sale price、促销日期、SKU和库存也按具体Variation维护。
- 所有可售Variations价格相同时，前台可显示单一价格；价格不同时，未选择前显示WooCommerce生成的价格范围，选定后显示该Variation的准确成交价。
- 即使当前所有Variations同价，也在每个Variation保存价格，避免后续个别规格调价时职责混乱。
- 缺少有效价格、已禁用或不属于合法组合的Variation不得购买；不能为了还原设计稿固定显示一个与真实选择不一致的金额。

### Display Only参考价格

- `display_only`不使用Regular price、Sale price或Variation价格；只使用经业务确认的`estimated_price_min`与`estimated_price_max`展示参考范围。
- 参考范围不是成交价、促销价或Offer，不进入购物车、结账、订单金额、税费、库存扣减或购买事件。
- 参考范围缺失时显示不含金额的展示状态与Contact入口；不得使用`0`、内部单价、旧目录价或推测值补位。

### 币种、来源与TEST规则

- 第一版基准币种为USD。后台录入纯数值，前端使用WooCommerce金额与币种格式API，不在模板、文案或字段中硬编码`$`。
- 当前暂不计算税费；未来启用税费、切换含税/未税显示或增加多币种均属于高影响变更，必须重新验证商品页、购物车、结账、订单、Schema和缓存。
- 正式价格由Website Manager或业务价格负责人确认；开发者只负责字段职责、权限、校验、显示和交易一致性，不从仓库内部单价、文件名或目录示例价推导正式售价。
- 未确认金额仅能用于名称和SKU均带`TEST`标识的Local或受保护Staging原型；D25开放批量录入前复核其回归价值并决定归档、删除或替换。
- 修改当前商品价格不应用于回写历史订单金额；改价前仍需检查促销宣传、CSV、外部报价和其他系统引用的一致性。

## 库存规则v1候选

### 数量跟踪与库存状态

- 标准可购买商品必须有明确库存状态。只有业务方能够持续提供并维护可信数量时才启用WooCommerce数量跟踪；若暂时只能确认能否销售，则使用库存状态管理，不录入`999`等虚假数量。
- 库存数量的单位必须等于一个购物车数量所代表的可售单位。例如每包20件的商品，库存`8`表示8包而不是160件；包装内数量继续由`Package Quantity`表达。
- `instock`表示当前可购买；`outofstock`表示不可购买；`onbackorder`只在业务明确允许延期交货，并确认预计交期、前台提示及履约责任后使用。
- 第一版默认禁止Backorders。未来启用时必须明确选择“允许并通知客户”或其他经批准策略，并回归商品页、购物车、结账、订单、邮件与库存扣减；不得静默超卖。
- WooCommerce原生低库存阈值和通知可在责任人、收件地址及阈值确认后使用；不另建重复库存提醒逻辑。

### Simple、Variable与套装

- Simple Product拥有独立SKU和可售单位时，在商品本身管理库存数量或库存状态。
- Variable Product默认由每个可售Variation独立管理SKU、数量、库存状态和Backorder策略；父商品只汇总可购买性，不同时再维护一套重复数量。
- 只有所有Variations确实消耗同一个物理库存池，而且业务无法或无需区分各组合数量时，才允许父商品统一管理共享库存；此时Variation继承父商品库存，不得父子双方重复扣减。
- 爱迪特锆块的Size×Shade候选若对应独立SKU和实物数量，应按Variation管理库存；具体合法组合与正式数量由业务方在D12～D18样本录入时确认，不阻塞通用骨架。
- 固定预包装且只按整套销售的套装作为Simple Product管理整套库存。若套装下单后从可单卖共享部件组装，原生Simple库存不会自动扣减各部件；第一版不得宣称已有组件联动，真实需求出现后另行评估Bundle/Composite、ERP同步或人工流程。

### 展示、缺货与停售

- `display_only`不参与交易库存：不显示`In stock`、`Out of stock`、数量、Backorder或低库存，不进入库存扣减，也不输出会暗示可购买库存的Offer信息。
- 临时缺货的已发布标准商品保持`publish`、目录可见、稳定Slug/URL、可索引和自身Canonical，使用`outofstock`与禁止Backorders阻止购买；没有永久停售结论时不得自动删除、301或`noindex`。
- 永久停售由业务方确认，不由库存数量或`outofstock`自动推导。严格一对一后继商品可进入301候选；无严格替代但有流量、外链、订单支持或独立内容价值时保留200停售页；无替代且无持续价值时返回真实404，必要时才评估410。
- 永久停售不删除订单历史、不复用SKU，也不把Canonical指向不相关商品。WooCommerce 11.0.0没有原生`discontinued`生命周期状态；真实200停售页出现前不提前增加字段或Schema代码。
- 正式库存数量、盘点频率、缺货处理和延期交货承诺由Website Manager或业务库存负责人维护；开发者负责字段职责、权限、校验、显示和交易一致性，不替业务方推测库存。
- 第一版不包含多仓库、供应商实时库存、ERP/WMS同步或组件级联动扣减。订单在哪个状态扣减、取消/退款何时回补，要在支付与订单状态方案确定后于D73～D78联调验证。
- 未确认库存只可用于名称与SKU均带`TEST`标识的Local或受保护Staging原型；不得将TEST数量作为正式可售承诺。

## 重量与尺寸规则v1候选

### 三层尺寸职责

- 产品规格尺寸描述商品本体或客户选择，例如锆块直径、厚度和设备适配尺寸；需要筛选或影响购买选择时使用Global Attribute或Variation，不写入WooCommerce Shipping字段代替物流数据。
- WooCommerce Shipping重量与长、宽、高描述一个购物车销售单位连同直接保护/零售包装后的发货数据，用于运费、装箱或承运商插件计算。字段保存纯数值，单位由全站WooCommerce设置统一提供，不在数值中写`mm`、`cm`、`in`、`g`或`lb`。
- 最终订单包裹可能包含多个商品、缓冲材料和外箱，其重量与外形由后续装箱、物流插件或履约人员决定，不能把某个商品的Shipping字段直接当成整张订单外箱。
- 产品净重、产品本体尺寸与发货毛重/包装尺寸可能同时存在。第一版只有确认需要客户查看时，才把净重或本体尺寸作为属性/规格展示；参与运费计算的字段优先使用可验证的发货数据。

### Simple与Variable职责

- Simple Product在商品本身维护物流重量与尺寸。
- Variable Product的各Variation若物流重量和尺寸相同，可继承父商品数据；若颜色、Size、Package Quantity等选择改变实际发货重量或外形，则在具体Variation覆盖对应字段。
- WooCommerce 11.0.0在Variation物流字段为空时会读取父商品值，因此空值代表“继承”而不应被业务流程解释为“尚未测量”。若某Variation真实数据未知且父值不适用，应阻止正式物流验收，而不是静默继承错误数据。
- 商品规格参与Variation，不代表必须改变物流尺寸；反之，包装规格改变发货重量或尺寸时，即使产品本体规格相同，也必须让实际可售Variation承担正确物流数据。
- `display_only`不参与普通结账和发货，不要求交易物流字段；页面需要展示的定制能力尺寸继续作为非交易规格内容维护。

### 单位、来源与物流边界

- 全站只能有一组WooCommerce基础重量单位和尺寸单位。2026-08-17 D15只读查询再次确认当前Local配置为重量`lbs`、尺寸`in`，与第一版美国市场方向一致；主要承运商、物流插件和真实单个销售包装样本仍未确定，因此该配置继续只作为开发环境事实，不冻结为Production物流标准。
- 导入、导出、API或物流插件需要不同单位时，使用WooCommerce的单位设置及`wc_get_weight()`、`wc_get_dimension()`等换算能力，不在模板和业务字段中另存互相冲突的单位版本。
- 正式重量和尺寸由业务方使用统一测量方法提供，必须说明测量对象是商品本体、单个销售包装还是最终外箱；开发者负责字段映射、单位配置、继承规则和运费联调，不根据图片或目录比例推测。
- 尺寸顺序固定按WooCommerce的Length×Width×Height维护，并在编辑帮助中显示当前全站单位；不得把直径、厚度或不规则形状强行塞入长宽高而不说明包装测量方法。
- 体积重、计费重、最小收费、地区、Shipping Class和外箱装箱算法由承运商及物流方案决定。不得通过人为放大商品重量来模拟体积重，否则会污染导出、订单和未来物流集成。
- 正式物流数据未知时可以先留空，不得用`0`冒充已确认；TEST值仅用于带TEST名称和SKU的Local或受保护Staging原型，并在D17～D18正式代表样本验收前替换。
- 重量和尺寸会直接影响运费与可配送性；后续改单位、物流插件或包装方式属于交易高影响变更，必须回归单件、多件、混合商品、不同Variation和地区运费。

### 组合数量与合法性

- 创建Variations前先计算理论组合数：各Variation属性值数量相乘。例如2个Size×2个Shade理论上有4个组合；理论组合不等于合法组合，更不等于必须自动生成全部组合。
- 业务方应提供合法组合表。只创建真实可售组合；不存在、禁用或未确认的组合不得通过通配Variation、虚假价格或虚假库存变成可购买状态。
- 每个可售Variation必须能唯一回答：属性组合、SKU、Regular price、库存真相源、可购买状态，以及物流数据是继承还是覆盖。任一项不清楚时只能作为TEST或待确认，不能正式发布。
- 不设置重复组合。若两个Variation覆盖同一属性选择，WooCommerce匹配结果和库存职责会产生歧义。
- 默认Variation只有在业务明确存在默认销售组合时才设置，而且必须指向合法、启用且可购买的Variation；否则让客户主动完成必要选择，不能为了减少点击随意默认第一个值。
- 组合数量增加会成倍扩大SKU、价格、库存、图片、物流和测试成本。出现大量理论组合或大量非法组合时，先评估减少Variation属性、拆分商品或调整购买方式，不以插件性能上限代替可维护性判断。

## SKU规则v1候选

### 标识职责

- 网站SKU是WooCommerce商品及变体的公开、稳定业务标识，不等同于数据库ID、商品Slug、仓库库位、内部编号或临时文件名。
- 来源优先级为：业务确认可公开且稳定的制造商货号 → DentAll分配的网站商品编号 → 明确带`TEST-`前缀的测试编号。
- 仓库内部编号和供应商货号必须分别保留来源含义；未经业务确认，均不得自动发布为网站SKU。
- 分类名称、促销状态、价格、库存状态等会变化的信息不得编码进SKU，避免分类调整或促销结束后被迫改号。

### 格式与唯一性

- 正式SKU候选仅使用大写英文字母`A-Z`、数字`0-9`和短横线`-`，不使用空格、中文、斜杠、货币符号或营销文案。
- SKU在全站所有商品和变体之间唯一；大小写不同不能用来表达两个不同商品。
- SKU发布后原则上不修改。确需修改时，必须检查订单历史、库存/采购对照、CSV导入导出和外部系统引用，并保留旧新映射。
- SKU不承担SEO职责；商品名称和Slug按各自规则维护。

### 主商品、变体与TEST数据

- SKU是标准可购买商品的发布闸门，不是创建草稿的技术闸门。资料未齐时允许Website Manager留空保存草稿并登记“SKU待补”，但不得将该商品正式发布。
- WooCommerce原生允许商品在没有SKU时保存甚至发布；DentAll不依赖该宽松默认值，正式发布检查必须单独确认SKU存在、来源明确且全站唯一。
- 简单商品使用一个独立SKU。
- 可变商品保留父商品SKU；每个可售变体另有唯一SKU。变体后缀只使用已确认、稳定且有映射表的属性值代码。
- 不直接把未经规范化的属性显示名拼进SKU；显示名改写时，既有SKU不应随之自动变化。
- 未确认数据统一使用`TEST-`前缀，例如`TEST-DTL-ZR-0001`；示例只用于解释格式，不是正式编码方案。
- SKU采用混合来源：业务确认可公开且可靠的制造商货号优先；不合适或不存在时，由`DentAll Website Manager`按统一规则分配DentAll自有SKU。
- `DentAll Website Manager`负责日常创建、重复检查和维护商品及变体SKU，开发者不参与逐个编号。批量导入、批量改号、历史数据迁移或系统校验异常才升级给开发者。
- Local或受保护Staging上的流程测试商品使用明确的`TEST-`前缀SKU；不得为了通过发布检查给正式商品编造临时SKU。
- `display_only`展示商品是否必须具有SKU，留到CR-005销售模式实现与验收时单独决定，不用该例外放宽标准可购买商品规则。
- 正式样本进入D18候选冻结或正式发布前仍需由业务方确认制造商货号是否允许公开，并形成DentAll自有SKU的最小编号规则；D12与D17 TEST原型不依赖该确认。

## 品牌数据治理v1候选

- 品牌回答“谁生产或以谁的品牌销售”，不能复制为Product Category、产品用途或Solutions。
- 品牌名称使用业务确认的正式公开英文名；大小写、空格、标点和常见别名统一映射到一个规范名称，避免出现重复品牌项。
- 每个商品原则上只记录一个主要品牌。制造商、经销商、自有品牌和OEM关系如需同时展示，应先明确业务语义，不能创建多个近义品牌凑数。
- 无品牌商品、ADS自有品牌和第三方原厂品牌必须分别确认；不得用`Unknown`、供应商文件夹名或仓库分类充当正式品牌。
- 商城名称保持`DentAll`；`ADS`是商品品牌，两者不得在品牌字段、商品名称或前台标识中相互替代。
- D9只形成名称、来源、负责人和重复项治理规则候选；品牌字段载体、归档URL、筛选与索引方案留到D52冻结。
- 品牌正式实现确认前不自建品牌CPT、不安装品牌插件，也不使用普通商品标签长期代替品牌。

| 后台英文名称候选 | Slug候选 | 是否筛选 | 是否可能做变体 | 示例与边界 |
|---|---|---:|---:|---|
| Material | `material` | 是 | 否/待确认 | Zirconia、PMMA、EVA；不重复建成分类 |
| Size | `size` | 是 | 是 | 必须带明确单位，例如`98 mm`；物流包装尺寸仍用Shipping字段 |
| Shade | `shade` | 视商品 | 是 | 牙科行业色号，例如`A2`；不与普通颜色混用 |
| Color | `color` | 视商品 | 是 | 普通可见颜色；不承载牙科色号 |
| Package Quantity | `package-quantity` | 是 | 是 | 表示可售包装内数量，例如`20 pcs`；不等同于库存数量 |
| Compatible System | `compatible-system` | 是 | 通常否 | 适配平台或系统；正式名称和术语待样本确认 |
| Compatible Device | `compatible-device` | 是 | 通常否 | 适配设备/手柄；若与System无法稳定区分则D12前合并评估 |
| Intended Use | `intended-use` | 待验证 | 通常否 | 仅在客户确实需要跨分类筛选时创建，不能复制Solutions或分类 |

### 属性选择与命名规则

- 同一含义且会被多个商品复用、用于筛选或形成购买选项时，才创建Global Attribute。
- 只属于单个商品且不需要筛选的普通参数优先使用商品级属性、描述或经验证的最小ACF字段，不污染全局属性库。
- 属性后台名称和Slug使用稳定英文；面向客户的显示文案未来使用可翻译输出，不把中英文同时写进同一个属性值。
- 属性项使用规范化显示值及单位，例如`98 mm`、`20 pcs`；不要同时创建`98mm`、`98 mm`和`98MM`。
- 尺寸、重量和数量必须区分测量对象：产品规格用属性，物流重量/包装尺寸用WooCommerce Shipping字段，库存数量用库存字段。
- `Shade`与`Color`分开维护；`Package Quantity`与库存数量分开维护；品牌、认证、分类和Solutions不混入属性项。
- 属性是否显示在前台、是否用于筛选、是否用于Variation是三个独立决定，不因创建了属性就默认全部启用。

## 变体规则

- 只有会改变价格、SKU、库存、图片或购买选择的属性才设为变体。
- “可筛选”不等于“必须做变体”；Material或Compatible System可以参与筛选但不生成购买组合。
- 控制变体组合数量；组合过多时重新评估商品拆分方式。
- 每个可售变体必须检查价格、库存状态、SKU和默认选择。
- 不可购买组合必须有清晰提示，不能静默失败。
- D9只定义属性到Variation的映射条件；合法组合、父子SKU实例、价格和库存留到D10及D14验证。

## 文章与页面字段

| 字段 | 内容类型 | 必填 | 规则 |
|---|---|---:|---|
| 标题 | Post/Page | 是 | 清晰描述主题，避免堆砌关键词 |
| Slug | Post/Page | 是 | 小写英文和短横线；发布后未经SEO确认不得修改 |
| 摘要 | Post | 是 | 用于文章列表和分享摘要，避免直接截断正文 |
| 正文 | Post/Page | 是 | 使用统一标题层级；不粘贴外部内联样式 |
| 特色图 | Post | 是 | 按约定比例上传，并填写可理解的alt |
| 分类 | Post | 是 | 至少一个主分类；D25后不随意新增近义分类 |
| 标签 | Post | 否 | 有明确聚合价值才使用，避免一文一标签 |
| 作者 | Post | 是 | 使用真实或统一品牌作者账号 |
| SEO标题/描述 | Post/Page | 建议 | 使用SEO插件字段；上线前抽样检查 |
| 内部链接 | Post/Page | 建议 | 链接相关商品、分类或内容，禁止使用临时Staging绝对地址 |
| 发布状态 | Post/Page | 是 | 试录阶段保存草稿；按审核规则发布 |

## 编辑录入验收

- 第一批只录入5～10个代表商品，覆盖简单商品、变体、促销、缺货、多图和资料下载。
- D18商品模型候选冻结前不要批量导入全部商品。
- D24前先录入3篇不同长度文章和1个固定页面，验证摘要、特色图、内链、SEO和发布流程。
- D25综合验收后才开放批量录入；此后未经确认不得改变核心商品字段、文章分类结构、Slug规则和固定链接。
- 每次字段改变记录迁移影响、旧数据处理和新增工时。
