## C1：Local与Staging媒体环境基线

### 结论

- Local与Staging都具备JPEG、PNG、WebP和AVIF图像处理能力，D11不需要为了常规商品图片安装图片处理插件。
- Local实际使用`WP_Image_Editor_GD`；LocalWP的PHP配置声明了`php_imagick.dll`，但DLL无法加载，Web运行日志也存在同一警告。当前GD足以继续JPEG、PNG、WebP和AVIF的骨架验证，Imagick问题不阻塞D11或D12。
- Staging实际使用`WP_Image_Editor_Imagick`，ImageMagick、Imagick、GD、WebP和AVIF均可用。
- 当前`DentAll Content Editor`仍只允许JPEG、PNG和WebP，单文件有效上限为5MB；PDF、SVG和AVIF未向该角色开放。该边界与D5～D6已验证结果一致，本周期未修改。
- Local与Staging使用不同主题，因此当前派生缩略图尺寸不是最终主题契约：Local启用Storefront 4.6.2，Staging启用Twenty Twenty-Five 1.5；D26还会进入DentAll主题主开发。C2应冻结源图比例、最低像素和安全区，不冻结当前临时主题生成的全部缩略图尺寸。

## C2：主图、图库与四端显示契约v1候选

### 效果图依据

- 已对照PC商品列表、PC商品详情、平板竖屏商品列表、平板竖屏商品详情、手机商品列表和手机商品详情共6张最终效果图。
- 商品列表在PC、平板和手机均使用规则的方形图片区域，商品本体在区域内完整显示；卡片高度不由原图纵横比决定。
- 商品详情在PC采用左侧主媒体＋下方缩略图条，在平板和手机采用上方主媒体＋分页圆点。三端都需要稳定的方形媒体区域，切换图片时不能推动下方购买信息跳动。
- 效果图中的产品大多使用白色或极浅中性背景、居中构图和柔和落地阴影；这应作为商品素材风格方向，而不是在前端硬编码每张图的阴影。

### 一张源图服务四端

- 商品主图、商品卡图和详情首图使用同一个WooCommerce Featured Image，不为PC、平板和手机分别维护三套商品图。
- WordPress/WooCommerce根据最终主题生成响应式派生尺寸；前端在列表和详情按实际布局选择合适的`srcset`候选，不直接加载原始大图作为所有缩略图。
- 编辑侧统一提供方形源图。C2冻结`1:1`画布方向，但具体推荐像素、最低像素和压缩体积留到C3验证后形成完整规则。
- 产品主体默认水平、垂直居中；画布四边保留约10%～15%的安全区。常规商品主体建议占画布宽高约70%～80%，不能贴边或被卡片裁切。
- 高、窄、长或横向产品继续放在方形画布中完整展示，使用`object-fit: contain`语义；不得为填满方框而拉伸、压扁或切掉关键部位。
- 商品图背景默认白色或统一的极浅中性色。透明素材在前台也必须落在确定的浅色画布上，不能依赖浏览器透明底色或出现棋盘格。

### 主图职责

- 主图用于商品列表、搜索结果、相关推荐、购物车缩略图及详情首屏，必须能在较小尺寸下识别商品，不依赖细小文字才能理解主体。
- 主图只展示一个清晰的可售对象或已确认的固定套装。若整套是销售单位，可以展示整套；若单件分别销售，不得用无法分辨销售边界的组合图作为唯一主图。
- 主图优先使用正面或最具识别度的角度，背景、光线、阴影和主体比例保持同类商品一致。
- 不在图片上额外烘焙商品名、价格、促销标签、库存状态、按钮或网站水印。这些状态由动态HTML输出，避免改价、改名、翻译和促销结束后图片失真。
- 商品包装本身真实存在的品牌、型号、认证标识可以保留；它们属于被拍摄对象，不等于在图片上后期叠加网页文案。正式使用前仍由业务方确认真实性、可读性和公开授权。

### 图库职责与顺序

- 每个标准商品至少需要1张可识别主图；建议提供3～6张有不同信息价值的图片，不因追求数量重复上传相同角度。
- 图库候选顺序：①主视角/可售单位，②包装或侧面/背面，③关键细节或尺寸参照，④使用或应用场景，⑤必要的标签/认证局部，⑥其他确有购买决策价值的视图。
- Featured Image不在Product Gallery中重复添加；前端将主图作为图库第一项，避免详情页出现两张相同图片。
- 同一系列不同商品可以使用统一摄影模板，但不能让多件商品共享一张无法辨认具体销售对象的主图。
- 图片中的尺寸参照不能替代结构化尺寸字段；规格、Variation和物流尺寸仍以WooCommerce字段和业务确认值为准。
- 效果图出现视频播放入口，但D11不把视频列为商品图片必填项，也不据此安装图库或视频插件；视频属于后续真实内容需求出现时的增强项。

### Variation图片职责

- 当Variation选择会明显改变颜色、外观、包装、套装内容或客户看到的实物时，为该Variation配置对应图片。
- 只有SKU、价格、库存、尺寸数字或不可见内部参数变化，而外观没有可辨识差异时，Variation继承父商品主图，不批量复制相同图片。
- Variation切换图片时保持同一1:1容器和稳定高度；图片加载中保留当前媒体框架，失败时回退父商品主图或统一缺图状态，不能显示破损图标。
- Variation图片仍描述该可售Variation，不把色号、尺寸、价格等动态文字后期写进图片。选中值继续由HTML和WooCommerce状态输出。

### 单图、多图和异常状态

| 状态 | 候选行为 |
|---|---|
| 单图 | 只显示主媒体；隐藏空缩略图条、无意义分页圆点和左右切换控件 |
| 多图 | 按业务顺序稳定显示；PC使用可操作缩略图，平板/手机使用圆点或触摸切换，并保留键盘入口 |
| 缺图 | 使用DentAll统一方形占位图和可理解替代文本；不显示文件名、破损图标或其他商品图片 |
| 竖长图 | 完整缩放到方形画布，允许两侧留白，不裁切产品顶部或底部 |
| 横长图 | 完整缩放到方形画布，允许上下留白，不拉伸填满 |
| 透明图 | 在统一浅色画布上渲染；检查白色产品轮廓仍可辨识 |
| 图片加载中 | 预留与最终图片相同的1:1空间，使用低干扰占位，避免布局位移 |
| 图片加载失败 | 回退统一占位图并保留商品链接和文字信息，图片失败不能阻塞购买或联系流程 |
| 重复图 | 录入自检时删除，没有新增信息价值的近似图不进入图库 |

### 四端显示边界

- 390、768、1024和1440px均保持商品卡图片区与详情主媒体比例稳定；实际卡片列数和详情布局由后续主题断点决定。
- PC详情缩略图需要可见选中状态，并支持鼠标和键盘；手机和平板的分页圆点不能成为理解当前图片的唯一信息，图库仍需可触摸、可键盘操作并具备明确焦点状态。
- 图片区域的收藏、缩放、促销等图标属于界面控件，必须由前端单独输出，不能烘焙在商品图内。
- 详情缩放或Lightbox若在D56实现，使用原始或足够大的派生图；C2只保留图像质量和安全构图条件，不提前冻结具体图库脚本。

### 责任边界与冻结状态

- 开发者负责1:1容器、响应式图像、`contain`规则、占位图、加载/失败状态、Variation回退和四端可访问性。
- Website Manager负责选择正式主图、排序图库、判断图片是否对应真实可售对象并确认授权；开发者不替业务方判断逐商品主图。
- 本节是D11 `v1候选`，用于D12 TEST原型和D17代表商品验证；D18真实样本通过前不标记为最终冻结。

## C3：像素、格式、色彩空间与压缩规范v1候选

### 现有素材只读抽样

- `dentall资料/`中可直接识别的商品位图共79张：PNG 23张、WebP 51张、JPEG 5张。
- 其中19张纵横比偏离1:1超过5%，9张至少一边不足800px；这些文件可以作为资料来源，但不能自动认定为合格主图。
- 多张现有PNG为2048×2048px，单张约1.4～2.1MB。它们具备足够像素，但直接上传会带来不必要的存储、缩略图生成和传输成本，应先按实际透明需求转成WebP或JPEG并压缩。
- 已发现640×640px方图、790×817px近方图及多张高度不足800px的超宽说明图；前两类不应被放大作为正式主图，超宽图应改造成方形图库图、拆分为HTML内容或放入商品长描述，而不是依靠图库缩略图承载细小文字。
- 现有素材的文件格式、尺寸和体积只表示“收到的源资料”，不表示业务授权、主图选择、英文内容或正式发布已经确认。

### 像素等级

| 用途/等级 | 像素候选 | 处理规则 |
|---|---:|---|
| 推荐商品主图、Variation主图和普通图库图 | 1600×1600px | 满足详情较大显示和高密度屏需要，同时低于WordPress默认2560px大图缩放阈值 |
| 常规可接受源图 | 1200×1200～2000×2000px | 不放大；按1:1画布、安全区和压缩规则输出 |
| 常规验收下限 | 1000×1000px | 可进入D12/D17验证，但需在详情和缩放状态检查清晰度 |
| 有条件旧素材 | 最短边800～999px | 仅在无法取得更高质量原图且实际显示清晰时使用；标记待替换，不保证放大或Zoom质量 |
| 不适合作为正式主图 | 最短边小于800px | 不放大、不锐化伪装；可降级为资料参考或要求业务方补源图 |
| 超大源图 | 任一边超过2560px | 上传前缩到实际需要的方形工作稿，除非有明确的精细Zoom用途和性能测试证据 |

- 项目推荐值从早期`1200×1200`候选细化为`1600×1600`优选、`1200×1200`常规接受、`1000×1000`常规下限。原因是详情效果图主媒体在PC接近较大展示宽度，同时需要兼顾高密度屏；这不是要求把低清图片人工放大到1600px。
- WooCommerce官方文档给出的通用最低建议为800×800px，新商品编辑器建议1000×1000px或更大。DentAll把800px保留为旧素材条件下限，而不是新素材交付目标。
- 网页图片质量只看实际像素和压缩结果，不使用`72 DPI`或`300 DPI`作为验收条件；打印DPI不决定网页上的清晰度。

### 输入格式规则

| 格式 | 第一版用途 | 规则 |
|---|---|---|
| WebP | 首选 | 适用于普通商品图、白底图及确认过透明边缘的透明图；兼顾体积与质量 |
| JPEG/JPG | 允许 | 适用于不需要透明背景的摄影图和复杂渐变图；输出后检查文字、边缘和产品细节 |
| PNG | 条件允许 | 仅用于确实需要无损细线、透明背景或JPEG/WebP出现明显瑕疵的图，不因“原文件是PNG”就继续上传大体积PNG |
| AVIF | 暂不作为编辑输入 | Local和Staging处理库均支持，但内容编辑角色未开放且两环境使用不同编辑器；第一版不要求业务人员提供AVIF，也不启用自动转换 |
| SVG | 禁止商品媒体上传 | 不进入普通媒体白名单；产品摄影图不需要SVG，图标由主题受控资产处理 |
| GIF/HEIC/HEIF/TIFF/BMP | 不接受 | 上传前转换为合格JPEG、PNG或WebP；第一版不以动画商品图作为必需能力 |

- 文件扩展名必须与真实MIME类型一致；将PNG、PDF或其他文件简单改名为`.jpg`不构成合法转换。
- 选择WebP还是JPEG以实际导出后的清晰度和体积为准，不为了统一扩展名反复有损转码。拿到已经严重压缩的JPEG时应从原始素材重新导出，不能先放大再转WebP。

### 色彩与图像数据

- 网站交付图统一转换为sRGB、8位/通道。CMYK、Adobe RGB、Display P3或未标记色彩空间在上传前转换并目视复核，避免Local、Staging、不同浏览器和设备出现颜色漂移。
- 应把EXIF方向真正应用到像素后再导出，避免缩略图和浏览器对方向标记解释不一致。
- 发布版移除GPS、拍摄设备、序列号、工作路径和无业务价值的EXIF/XMP元数据；素材来源、作者、授权和版权信息记录在项目素材登记表，而不是只依赖容易在压缩中丢失的嵌入元数据。
- 不主动增加锐化、降噪或AI放大来伪造产品细节。涉及色号、牙色、材料透明度等会影响业务判断的图像，不得未经业务确认进行改变颜色含义的修图。

### 压缩与体积分级

| 等级 | 单张输出体积候选 | 处理方式 |
|---|---:|---|
| 推荐 | 普通JPEG/WebP不超过350KB | 作为大多数1600×1600白底商品图目标；以目视质量通过为前提 |
| 透明/细节图推荐 | WebP或必要PNG不超过500KB | 透明边缘、细线或标签细节确有需要时采用 |
| 需要复核 | 350～750KB | 检查是否使用错误格式、像素过大、重复元数据或过高质量参数 |
| 默认退回重导 | 超过750KB | 无明确细节价值时先压缩或换格式；不得以“低于5MB”视为已优化 |
| 技术硬上限 | 5MB | 现有内容角色上传边界，不是内容制作目标 |

- JPEG/WebP导出质量可从约75～85区间开始测试，但不同工具的质量数字不可直接比较，最终以100%查看产品边缘、标签和渐变是否可接受为准。
- 不允许为了命中体积指标而使包装文字出现明显块状、光滑边缘出现光晕，或使色号、认证标识等产生误读。
- 每张图独立判断；纯白背景单品通常应远低于350KB，复杂应用场景可以合理更大，但需要说明其独特信息价值。
- 页面性能以后续响应式派生图、懒加载和缓存共同控制；D11不安装优化插件，也不自动把全部原图转成单一格式。

## C4：文件名、alt与媒体元数据规范v1候选

### 现有文件名只读审计

- 共检查`dentall资料/`下79张位图：18个文件名含空格，33个含非ASCII字符，38个含大写字母，41个属于纯序号、时间戳、微信/ChatGPT导出名或带`final/copy/最终/副本`等弱语义版本标记。
- 典型问题包括`1.jpg`、长时间戳、`微信图片_...`、`ChatGPT Image ...`和`sport mount guard-2.webp`。这些名称无法稳定说明销售对象、视角或用途，也容易在批量上传后降低媒体库检索效率。
- 本次不批量重命名现有素材，也不改WordPress媒体库或已发布URL；规则从“正式上传前交付检查”开始执行。历史素材在被选入商品原型或正式商品时逐个治理。

### 上传前文件名规则

候选结构：`{brand-or-maker}-{product-or-model}-{view-or-purpose}[-{variation}].{ext}`。

- 使用小写英文字母、数字和连字符；不用空格、下划线、中文、括号或连续连字符，扩展名统一小写。
- 至少表达“什么商品”和“什么视角/用途”。常用用途词包括`front`、`back`、`side`、`package`、`detail`、`in-use`、`size-guide`和`color-chart`。
- 只有图片确实只对应某个Variation时，才追加经过确认的规格值；不得把并不影响画面的属性机械写入每张图片。
- 可以使用已批准公开的品牌、型号或SKU；不得包含进价、库存、促销日期、个人信息、客户名称、服务器路径或未批准公开的内部编号。
- 不使用`final`、`new`、`copy`、`v2`等短期版本词，也不保留相机、聊天工具、AI工具或下载平台的默认导出名。版本和来源在素材登记表中管理。
- 文件上传后会形成公开且可能被引用的URL。已发布媒体不得只为“更好看”而随意重命名或重新上传；确需替换时另行评估引用、缓存、SEO和回滚影响。

示例：

| 场景 | 推荐文件名 | 不推荐文件名 |
|---|---|---|
| 锆块正面主图 | `aidite-zirconia-block-front.webp` | `202510231634396272.png` |
| A2色、98mm规格专用图 | `aidite-zirconia-disc-a2-98mm-front.webp` | `最终版A2色-2.png` |
| 运动护齿套颜色表 | `sports-mouthguard-color-chart.webp` | `微信图片_20260716163057_123_2.png` |
| 抛光套装包装背面 | `hp0103g-polishing-kit-package-back.jpg` | `IMG_0048 FINAL.jpg` |
| D12测试商品主图 | `test-simple-product-front.webp` | `1.jpg` |

正式品牌名、型号、SKU、规格值和商品归属属于业务内容，由Website Manager或业务方在选图时确认；开发者负责命名结构、校验规则和安全边界，不替业务方猜测事实。

### WordPress媒体字段职责

| 字段 | 本项目职责 | 录入规则 | 示例 |
|---|---|---|---|
| Title | 媒体库中的可读标签，便于编辑检索和区分素材 | 使用简洁、自然的英文；上传后检查系统从文件名自动生成的值，不把文件名原样当最终标题 | `Aidite Zirconia Disc – Front View` |
| Alternative Text（alt） | 图片在当前内容语境中的可访问替代含义；媒体库值作为默认值 | 用简洁自然的英文说明对象及真正有意义的视角/差异；不写`image of`，不堆关键词，不抄文件名 | `Aidite zirconia disc, front view` |
| Caption | 需要在页面中可见的补充说明 | 普通商品图默认留空；只有来源、演示条件、比例非实物或合规提示确需展示时才填写 | `Colors may vary by monitor.` |
| Description | WordPress附件的较长说明，能否公开取决于主题和附件页面 | 第一版默认留空；不得存客户隐私、内部备注、许可证密钥或唯一授权凭证 | 必要时写非敏感的公开编辑说明 |

- Title、alt、Caption和Description不是四份同义文案，禁止把同一句话机械复制到全部字段。
- 媒体库alt只是可复用默认值，同一图片在不同页面可能承担不同功能。最终主题输出必须结合链接文字、商品标题和周边内容判断，必要时覆盖或置空，避免屏幕阅读器重复朗读。
- 商品主图或图库中的信息性图片通常需要alt；纯装饰图应由主题输出空`alt=""`。不能用空alt掩盖缺失的商品信息，也不能用文件名自动填充alt。
- 包装图只概括当前购买判断所需的可见信息，不逐字抄录所有包装文字。重要规格、认证、警告和使用条件应同时以可检索的HTML或受控资料呈现。
- Variation图片的alt只加入画面中真实可见且有区分价值的规格，例如颜色或尺寸；价格、库存和促销仍由WooCommerce动态文本表达。
- 第一版前台语言为英语，因此正式媒体Title、alt和公开Caption使用英语。内部素材来源、授权状态和业务确认记录使用中文登记，不混入公开媒体字段。

### 三类文件通道

| 通道 | 适用内容 | 存储与交付 | 关键边界 |
|---|---|---|---|
| 公开营销资料 | 已批准的产品目录、说明书、数据表、公开证书副本 | 可进入WordPress媒体库或经批准的公开静态存储，并在页面提供明确下载链接 | 任何知道URL的人都可能访问；不得包含价格底表、个人信息、内部批注或未公开参数 |
| 购买后受控下载 | 只有购买者应获得的数字文件 | 使用WooCommerce Downloadable Product及受保护下载目录，优先验证Force Downloads或Cloudways支持的X-Accel-Redirect | 不从普通媒体库选取文件；不使用`Redirect only`作为保密方案；需测试订单权限、过期、次数和撤销 |
| 内部/授权证据 | 合同、许可证、报价底表、原始仓库表、客户资料、审批记录、源文件 | 企业控制的私有云盘、文档系统或受限归档；登记表只记录证据位置 | 不进入WordPress、公开Web目录或源码Git；共享遵循最小权限和人员离场撤权 |

- “密码保护页面”“未在导航展示”“noindex”都不能保护普通媒体库文件的直链。公开媒体库只用于接受公开访问的文件。
- 第一版若只提供访客可下载的产品说明书，不应为了“下载按钮”把实体商品改成Downloadable Product；公开资料与购买后授权文件是两种业务语义。
- 当前`DentAll Content Editor`继续只允许JPEG、PNG和WebP，不开放PDF、DOCX、XLS、ZIP或其他文档。后续确有公开PDF需求时，仅为已实现并验收的`DentAll Website Manager`增加最小PDF能力。
- 购买后受控下载属于交易权限链路，最晚在D63“参数、认证和下载”阶段结合Cloudways/Nginx能力实施和回归；D11只冻结候选边界。

### 公开PDF验收规则

- 公开输入只接受真正的PDF；DOCX、XLS、TXT和ZIP不直接作为商品公开附件。源文档先清理并导出PDF，保留内部源文件和派生关系。
- 文件名沿用小写英文和连字符，可使用`{brand}-{product}-{document-type}-{language}-{version-or-date}.pdf`。文档版本/日期会影响内容有效性，因此允许使用经过业务确认的版本或ISO日期，不使用含糊的`final`、`new`或`最新版`。
- 普通公开PDF目标不超过5MB。超过5MB应先压缩图片、移除重复资源、拆分或改用经批准的外部权威地址；不能通过提高WordPress上限掩盖18.3MB目录的性能与存储问题。
- 上传前同时验证扩展名、MIME与文件签名，不信任浏览器上报的Content-Type；执行恶意文件扫描，并检查嵌入附件、JavaScript、启动动作、表单、外链、隐藏批注、修订痕迹和敏感元数据。
- 公开PDF默认不得加打开密码或复制限制。这些限制不能代替访问控制，也会降低可访问性和后续归档能力。
- PDF应包含可选择的真实文本、正确语言、文档标题、标题层级和合理阅读顺序；长文档提供目录/书签，图片和图表提供必要说明。扫描件应OCR并人工校对，不能只交付整页图片。
- 下载链接使用能说明内容、格式和必要体积的英文文案，例如`Download the zirconia disc technical data sheet (PDF, 1.8 MB)`，不用孤立的`Click here`。
- 会直接影响购买、安全、兼容性或合规判断的关键内容必须同时以可访问HTML呈现；PDF是补充资料，不是隐藏必要商品信息的唯一载体。

### 授权登记与发布闸门

`project-docs/CONTENT_ASSET_REGISTER.md`是项目素材状态的权威索引，本周期已补充授权登记字段与统一状态。正式发布前必须完成：

1. 分配资产ID，记录权利人、来源及原始文件位置。
2. 记录允许的商业用途、渠道/地区、是否可修改/翻译、署名要求、有效期和版本。
3. 将合同、邮件或许可证等证据放在企业控制的私有位置；登记表只保存证据位置和结论。
4. 完成安全、敏感信息、内容事实、PDF可访问性和文件体积检查。
5. 由业务批准人确认`批准公开`后才能上传，并回填公开URL、版本和发布日期。
6. 授权到期、内容失效或权利人撤回时，停止新增使用，移除页面链接，评估删除/替换文件、重定向或`410`，并处理CDN/页面缓存和搜索索引。

- `项目提供`、`供应商发送`、`网络可下载`和`AI生成`都不自动等于允许商业网站公开使用。
- 素材授权、内容事实与技术安全是三道独立闸门；任何一道未通过都不得正式发布。
- 删除媒体附件不能保证第三方缓存、搜索引擎或已下载副本立即消失，因此敏感文件必须在上传前阻断，撤回流程只是补救措施。

## 可复用核心思想

- “服务器能处理某种格式”“WordPress允许管理员上传”“业务角色应该上传”是三层不同边界。图片库能力决定技术可行性，WordPress MIME决定平台入口，角色白名单决定最小业务权限，不能互相替代。
- 业务上传上限取服务器、PHP POST、WordPress过滤器和角色规则中的最小值；只查看`upload_max_filesize`很容易得到错误结论。
- 不同主题会改变WooCommerce派生图片尺寸。内容生产规范应优先冻结足够清晰的源图、稳定比例和主体安全区，再由最终主题生成合适的响应式尺寸。
- 本地与Staging可以使用不同图像处理器，只要共同输入格式和可见结果通过验证；不应为了环境完全相同而提前安装不必要组件。
- 一张商品图片同时服务列表、详情、搜索和购物车时，安全构图比单个页面“刚好填满”更重要。固定方形画布、`contain`和一致留白可以减少跨端裁切返工。
- 主图、图库和Variation图片解决的是三个不同问题：主图识别销售对象，图库补充购买信息，Variation图片反馈选择后的可见差异。把它们混为一套重复图片只会增加维护成本。
- 动态价格、库存、促销和选项不能烘焙进图片；把变化频繁的业务状态留给结构化HTML，才能保持可访问性、SEO、改价和未来翻译的一致性。
- 图片规范不能只写一个“最大5MB”。服务器硬上限解决的是请求能否进入系统，内容目标解决的是页面是否快速、存储是否合理、派生图是否稳定；两者相差一个数量级也很正常。
- 统一格式不等于统一质量。应根据透明、摄影、细线和渐变选择WebP、JPEG或PNG，再用目视检查约束压缩损失，而不是要求所有文件机械转换成同一种扩展名。
- 像素不足时放大会增加文件尺寸，却不会恢复真实产品细节。把低清素材明确降级为“条件旧素材”比AI锐化后冒充高清更安全，尤其适用于色号、认证和医疗相关产品图。
- 好文件名解决资产识别和URL稳定性，alt解决当前页面中的可访问含义；两者目的不同，不能靠文件名自动生成合格alt。
- 媒体库字段是资产级默认值，页面输出是语境级决策。同一图片作为商品信息、链接入口或纯装饰时，合适的alt可能不同，最终组件必须保留覆盖能力。
- 任何可能公开输出的CMS字段都不应被当作私密档案。版权凭证、客户信息和内部审批应进入有权限与审计边界的登记系统，不能只藏在媒体Description中。
- `noindex`控制搜索引擎意愿，页面密码控制页面入口，媒体URL控制文件读取，三者不是同一安全边界；私密文件必须使用真正的鉴权交付和非公开存储。
- 授权、事实和安全是三道相互独立的发布闸门。来源合法不代表内容准确，内容准确不代表文件安全，技术可上传也不代表允许公开。
- 撤回成本在上传公开目录的瞬间就已经产生。与其依赖删除、缓存刷新和搜索引擎下架补救，不如在发布前用明确状态阻止未授权或敏感文件进入Web根目录。
- 单个底层识别函数的返回值不等于真实上传结论。文件安全验收必须走与生产入口相同的完整处理链，覆盖角色白名单、体积过滤、核心类型检查、存储和错误输出。
- 测试公开文件边界不能只看“页面有没有链接”。上传后用匿名HTTP读取并校验内容，才能证明直链是否真的公开；测试结束还必须验证文件和派生物已经清理。
- “推荐尺寸”不能反向要求放大低于推荐但仍合格的源图。推荐值用于指导新素材生产，接受区间用于判断现有素材是否可安全使用；混淆两者会制造虚假细节和无意义体积。
- 负向测试样本必须在文件名、登记和流程中同时标明用途。否则低清、未授权或错误格式样本很容易被后续人员误当作待发布内容。
- 所有准备长期运营的独立站都需要回答素材来源、显示契约、质量标准、命名与可访问性、公开权限、上传安全和验证交接等问题；具体安排几天以及采用1:1、1600px、350KB或5MB等参数，应由业务规模、设计、平台和基础设施决定，不能把DentAll或WooCommerce的当前数值当作行业统一标准。
- 媒体治理可以被推迟，但成本不会消失。内容量扩大后再统一比例、重命名、压缩、补alt、重绑Variation图片或清理敏感文件，返工通常随“商品数量×每个商品的媒体数量”放大，并连带影响URL、SEO、缓存、备份和发布回归；因此应在批量录入前先冻结可执行骨架。
- 媒体规范的长期价值不是记住几个像素和体积数字，而是把设计、开发或编辑个人脑中的隐性经验，转换成业务、素材、编辑、开发、测试和交接人员都能执行的生产契约；即使人员、主题或平台变化，判断依据仍能被复用和审计。
- 面向Shopify＋WooCommerce双平台能力建设，应先掌握跨平台不变量，再学习各自实现：两者都要解决商品媒体职责、响应式图片、alt、文件公开性、授权、上传限制和生命周期，只是媒体存储、主题渲染、权限模型、应用/插件扩展点及受控下载机制不同。Day11已验证的是WooCommerce/WordPress实现；Shopify对应机制属于后续实测课题，不能未经验证直接宣称等价。
