## Cloudways支持确认与待核实项

支持工单编号保存在私有证据中。技术支持工程师表示平台自助Point-in-Time Restore只会覆盖**所选原应用**；如果要验证指定历史点且不改变来源，可由支持从异地调取`2026-10-06 18:00:13 UTC`的精确备份，手动导入同服务器新应用的独立文件与数据库。他表示新应用可在导入前设`Application Access OFF`并保持到导入结束，来源应用不变；同服务器新增应用不另收费。客服已报告取件和静态导入完成；目标与来源库表名集合已独立核对一致，但表内内容、来源完整不变量及实际账单尚未独立复核。

支持此前表示原始ZIP和SQL可仅暂存于**新应用非Web目录**（优先新应用的`tmp`），解包/导入前记录大小和SHA-256，验证后删除暂存文件；实际取件方式与此前描述不同：客服称异地备份取出即为解开的目录，不存在本轮可供核对的ZIP。其终端截图显示新目标`tmp`下有`mysql`、`private_html`、`public_html`及大小、哈希命令，不能据此虚构原始ZIP的SHA-256。新应用最终运行文件进入其自身`public_html`是正常恢复目标，不等于允许把原始备份暴露在Web根目录。客服已确认精确恢复点时间并报告新目标站点文件复制完成、目标`wp-config.php`的数据库连接已改、权限已重设；导入前报告SQL不含`CREATE DATABASE`、`USE`或指向其他库的限定写入语句，并在导入后报告完成、目标Access仍OFF。数据库表数与表名已独立读回，暂存SQL mode=`0600`已有客服截图；文件与SQL的详细清单、导入日志、表内记录、跨应用读取边界及哈希独立复算仍待核。Cloudways[私有目录说明](https://support.cloudways.com/en/articles/5123384-securing-app-configuration-files-in-private_html-folder)指出`private_html`也会进入常规备份，因此临时备份优先放`tmp`以免被新应用后续备份重复收录；[磁盘清理说明](https://support.cloudways.com/en/articles/5123297-optimize-your-server-disk-space)列出应用级`tmp`的独立路径。

Ajith明确答复：Cloudways没有内置阻断服务器出站HTTP/HTTPS或任意TCP/UDP的选项；`Application Access OFF`是其可提供的控制。同服务器因此不能只对新应用阻断出站而保留来源正常运行。[Application Access说明](https://support.cloudways.com/en/articles/5124808-how-to-stop-access-to-your-application-on-cloudways)证实OFF会暂停该应用网站访问和应用Cron，但IP白名单、应用访问开关和默认Cloudways域名不能据此证明首次动态运行不会发送邮件、Webhook或支付请求。来源数据库含既有TEST客户/订单和SMTP配置；恢复副本若启动WordPress，还可能执行WooCommerce Action Scheduler并接触共享Redis。支持此前建议停用SMTP插件及使用临时mu-plugin，但该建议未经过DentAll验证，不能代替可验证的出站隔离。支持确认同一历史备份可由其恢复到另一台新Cloudways服务器；新服务器本身仍没有上述出站阻断能力，不能满足D106首次动态运行闸门。费用答复仅指向通用价格页，未提供最低配置或具体账单；未创建或授权付费服务器。

客服补充确认暂存目录对应`2026-10-06 18:00:13 UTC`恢复点，目标Access保持OFF且来源未改。基于此，已在客服聊天中授权**仅一次离线静态导入到独立恢复目标**；指令要求先检查SQL内的`CREATE DATABASE`/`USE`，使用仅能写目标库的凭据，且只改目标文件与`wp-config.php`。禁止执行PHP、WP-CLI、Cron、Action Scheduler、插件迁移、动态HTTP、SMTP、共享Redis清理或服务器级配置变更；若必须做这些操作则停止并反馈。客服先回复“Import has been completed”，后续称导入无错误、来源未动，并声称uploads逐文件摘要零差异；对照首张截图的暂存/目标路径与文件计数已核，其余截图、完整导入日志及哈希独立复算仍待核。数据库表名核对是独立的局部证据，不能代替内容完整性验收。

## 可复用核心思想

- **跨平台不变量：** “备份任务成功”“备份包可读”“数据可导入”“完整站点可安全运行”是四个不同的证据层级；只有在独立目标完成恢复并验证业务状态，才能宣称具备恢复能力。
- **WordPress/WooCommerce当前实现：** 文件、数据库和媒体需要同一时间点对应；`wp-config.php`、Cron、队列、SMTP、Webhook、支付与对象缓存可能在首次PHP请求产生副作用，恢复演练必须先隔离再运行。
- **其他平台对应机制：** 托管平台通常提供备份点与访问开关，但应逐项核实能否导出指定历史点、恢复到独立目标及控制出站；不能从“有备份列表”推断其恢复语义。Shopify或其他平台的具体导出/恢复边界须按平台实际能力另行验证。
