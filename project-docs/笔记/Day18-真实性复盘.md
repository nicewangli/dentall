- **已技术验证**：配置或代码已落地，并有Local或Staging运行证据。
- **TEST机制通过**：使用明确TEST数据证明结构与状态成立，但不证明正式业务内容正确。
- **候选**：规则或设计已形成，仍需后续实施或业务确认。
- **待验收**：实现或前置条件存在，但指定人员、环境或恢复路径尚未通过。

这些工作类似建筑的地基、门禁和管线：它们真实存在，但不会自动呈现为已经装修完成的商城页面。对应到WordPress，就是环境、capability、Product/Variation模型、SEO输出与部署边界已经有基础，主题组件和完整交易模板仍未开始。

## 四、造成迷茫的根因

1. **进度语义错位**：D日检查点容易被理解成已经消耗相同数量的完整工作日或应该出现对应比例的可见前台；工时未统计本身不是问题。
2. **完成状态过粗**：技术验证、TEST机制、候选冻结和正式业务验收都曾使用“完成”表述。
3. **阶段设计前置后台**：D1～D25主要建设内容生产线，D26才进入正式前端，天然缺少视觉反馈。
4. **文档与验证缺少展示出口**：大量规则、测试和决策存在，但没有形成开发者本人可复演的短闭环。
5. **没有可持续成就感机制**：计划按专业领域横向推进，缺少每隔数日就能从后台走到前台的纵向演示。

## 五、从D19开始生效的真实性规则

1. D1～D120采用结果驱动的计划检查点口径；实际完成速度快于计划时可以直接推进下一检查点。
2. 实际工时由用户按需记录，不作为完成门槛；需要统计时记录真实值，不得用计划时长代填。
3. 每项成果必须标注为“候选、已配置、TEST机制通过、技术验证、人员验收、业务验收或Production验收”之一。
4. “完成”只用于授权范围已经落地、验证且没有所需验收缺口的事项；外部等待和未覆盖环境必须单独列出。
5. 每个工作日最多保留3个验收结果；至少包含一个可直接查看、运行或由用户复演的证据。
6. 每3个计划检查点至少组织一次短演示；如果连续只有文档和规则，应暂停并检查是否出现过度治理。
7. 文档只在承担事实入口、决策、操作、测试或交接职责时新增；同一结论优先链接，不重复扩写。
8. 不再报告未经证据支持的整体完成百分比。计划位置、能力状态和人员/业务验收分别报告；工时仅在用户选择统计或出现延期时加入。
9. 用户发现实际速度慢于预期时主动说明；届时再复核里程碑、依赖和低优先级范围，不因速度快而主动放慢。

## 可复用核心思想

- 跨平台不变量：计划序号、实际投入、技术验证、业务验收和用户可见价值是五个不同维度，任何项目都不应压缩成一个“完成百分比”。
- 跨平台不变量：看不见的基础设施可以是真成果，但必须定期通过短闭环演示把技术资产转化为团队理解，否则文档越多，项目反而越显得抽象。
- WordPress/WooCommerce实现：角色capability、Product/Variation、SEO元数据、CSV、数据库和uploads分别属于不同证据面，单个测试通过不能外推整个商城完成。
- Shopify或其他平台同样需要区分主题可见成果、后台数据模型、员工权限、导入导出和正式上线状态；具体机制需按平台验证，不能复用WooCommerce的字段结论。
