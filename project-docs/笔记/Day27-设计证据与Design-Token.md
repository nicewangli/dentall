## C1已冻结：冲突处理口径

1. A层视觉意图优先于增强稿和单页随机差异；共用Header、Footer、颜色和组件规则优先于某一张商城截图的局部变化。
2. 已确认需求、WordPress/WooCommerce真实状态和API输出优先于AI图中的文案、价格、库存、订单、结账步骤或交互推测。
3. 1024px采用紧凑导航方向，完整PC导航从`>=1200px`开始；B-稿中的完整导航不覆盖该口径。
4. 手机Footer不得因截图省略而删除内容；后续采用堆叠或可访问折叠，并保证链接可达、键盘可用。
5. 第一版不纳入只存在于截图的多语言/多币种、Wishlist、Buy Now、Wallet、Notifications、社交登录、固定手机底栏和商品视频。
6. 搜索分类选择器、Mini Cart详细行为和Storefront手持底栏的最终处理留D31～D33按真实需求确认；C1不提前实现。
7. Newsletter服务商、隐私同意、错误恢复仍未确认；支付、社交和安全标识只允许使用正式启用服务或官方授权资源。

### 字体加载边界

- Storefront 4.6.2当前通过`storefront-fonts`从Google Fonts加载`Source Sans Pro:400,300,300italic,400italic,600,700,900`。
- C2建议只使用现有400/600/700，避免浏览器合成500字重；本轮不新增字体文件、CDN或请求。
- 这仍继承父主题现有远程字体依赖。若后续选择纯系统字体并移除该请求，必须单独修改PHP加载逻辑并验证隐私、性能、Embed和回滚，不能伪装成C3单文件小改动。
- 正式Logo字体、品牌字体文件及许可证缺失不阻塞通用骨架，但会阻塞正式品牌视觉验收。

## 可复用核心思想

- 跨平台不变量：设计还原先冻结证据层级，再提取Token，最后实施组件。截图能证明视觉意图，但不能自动证明业务数据、交互状态或平台流程；把三者混在一起会导致最昂贵的返工。
- 跨平台不变量：视口宽度不等于内容容器宽度。容器、gutter和断点必须用真实长文本、空状态和溢出证据验证，而不是照抄画布尺寸。
- 跨平台不变量：颜色“看起来接近”不等于可访问。装饰色、正文色、控件边界和Focus的职责不同，同一个低对比色不能因为品牌一致性而承担所有语义。
- WooCommerce/WordPress实现：子主题CSS应复用父主题加载顺序并使用项目名前缀减少冲突；全局样式必须回归Cart、Checkout、Account和WooCommerce Notice等真实状态，不能只看首页截图。
- Shopify或其他平台对照：Shopify主题同样需要Design Token、Section边界、动态数据和四端验证，但Liquid Section、Theme Settings与WordPress Hook/Customizer机制不同；具体映射仍需在对应平台验证，不能把Storefront实现当成跨平台标准。
