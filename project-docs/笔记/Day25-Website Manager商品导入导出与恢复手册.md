# Day25 Website Manager商品导入导出与恢复手册

## 相关笔记

- 当日综合验收：[[Day25-综合验收与批量录入开放]]

## 第一版结论

- Website Manager使用WooCommerce原生商品Import/Export，不使用DentAll自定义导入器。
- 当前已批准的CSV范围是“Simple模板v1、仅新增Draft”；暂不更新已有商品，也不通过CSV导入Variable父商品或Variation。可变商品继续使用已验收的WooCommerce后台单录流程，待单独完成父子CSV验收后再扩大范围。
- 每批导入前的全量商品导出是不可编辑回导的数据快照；新商品填写使用另存的受控空白模板，两类文件不得混用或互相覆盖。
- 每批导入前由Website Manager导出商品CSV；开发者/管理员负责应用文件＋数据库定期备份和实际恢复。
- 每位工作人员使用本人独立账号。新建商品可以查到创建账号，但WordPress/WooCommerce原生功能不能完整记录商品后续每次价格、库存、分类、图片或状态修改。
- 第一版没有整批一键撤销；可审计依靠独立账号、原生有限记录和商品CSV批次登记共同完成。

## 职责分工

| 事项 | Website Manager | 开发者/管理员 |
|---|---|---|
| 商品事实、SKU、价格、库存、分类、属性和图片 | 准备、核对、录入 | 不替业务方猜测 |
| 导入前全量商品快照 | 每批自行导出、原样保存 | 必要时协助差异分析 |
| 新商品空白录入模板 | 复制已验收模板后填写新商品 | 验收模板列、状态和映射；业务结构变化时更新版本 |
| 应用文件＋数据库备份 | 查看/记录已确认的备份时间 | 配置、核对、保留和恢复 |
| 原生CSV导入 | 按本手册执行小批量新建Draft | 处理异常、已有数据变化和恢复 |
| 批次记录 | 填写操作者、文件、结果和抽查 | 复核高风险异常及恢复证据 |
| 文章和Page | 使用WordPress编辑器逐篇/逐页维护 | 处理权限、URL和技术异常 |

Website Manager不得获得Cloudways、数据库或服务器恢复权限。文章和Page日常不走CSV导入。

## 导入前必须满足

- 使用本人Website Manager账号，不能共享账号。
- 当前环境必须是批准的受保护Staging；不要在Production做首次测试。
- 最近一次应用文件＋数据库备份时间已经由开发者/管理员确认并记录。
- 本批CSV只包含新商品，不包含现有商品ID；SKU均为未使用的新值。
- 当前Simple商品的`Published`列必须为`-1`。
- 全量快照与录入模板是两个文件：不在全量快照上直接填改；只复制已验收的空白模板建立本批源CSV。
- 不把WooCommerce中文全量导出文件原样作为新建模板；当前导出存在重复中文“交叉销售”表头，并包含现有ID/SKU和环境图片URL。
- 当前WooCommerce全局币种已确认为`USD`；价格列只填纯数值，不写`$`、`¥`或自行换算币种。
- CSV只通过“商品 → 所有商品 → 导入”使用，不作为普通媒体内容发布；文件不得包含账号密码、API密钥、订单、客户个人信息或内部敏感资料。
- D25技术验收已通过后，Website Manager可以在受保护Staging按本手册开始小批次Draft录入；Production首次导入仍须重新验收。

任一条件不满足时停止，不要尝试通过猜测映射或重复上传解决。

## 第一步：导出商品数据快照（保持原样）

1. 进入“商品 → 所有商品”。
2. 点击商品列表顶部“导出”。
3. 第一版备份快照保留全部核心列、全部商品类型和全部分类；自定义元数据是否导出由开发者另行确认，不自行勾选。
4. 下载完成后，不在该文件中填写新商品，也不覆盖原文件；保留WooCommerce生成的日期时间文件名。
5. 把文件名、保存位置、SHA-256、导出时间和当时应用备份时间写入`CONTENT_ASSET_REGISTER.md`的商品CSV批次登记。

商品CSV可以帮助比较或定点修复商品数据，但它不包含完整uploads文件、全部插件元数据、网站设置和数据库关系，因此不是完整网站备份。

## 第二步：复制受控模板并检查新商品CSV

WooCommerce官方允许从现有商店导出、官方sample CSV或产品CSV schema三种方式建立导入文件。DentAll第一版采用“受控TEST示例/官方schema → 清洗为空白模板 → Website Manager复制填写”的方式；这不等于把当前全量商品快照直接回导。

1. 使用开发者与Website Manager已经验收的模板结构。D25 TEST源文件`dentall-c3-simple-test-v1.csv`证明22列Simple结构可用，但其中TEST数据行不得当作正式商品事实；正式批次复制模板后替换为业务确认内容。现有商品数据行、ID、旧SKU、环境图片URL和不使用的Upsells/Cross-sells列不得进入模板。
2. 每一批从已验收模板复制新文件，保留模板版本或SHA-256；禁止直接改写模板母版和导入前全量快照。
3. 价格列只填写经业务确认的纯数值；币种由目标环境WooCommerce全局设置决定，第一版必须为`USD`。

4. 每个商品使用新SKU；不得复用、大小写变形或猜测现有SKU。
5. `ID`列留空或不提供；不得把导出文件中的现有ID带入新建批次。
6. `Published`必须明确填写`-1`。缺少该列时原生导入可能把新商品发布。
7. 当前Simple模板v1不包含Parent或Variation行；不得自行增加Variable父商品、Variation或父子SKU映射。需要批量导入可变商品时先停止并申请独立验收。
8. 价格、库存、单位、分类、属性或图片URL不确定时保持本批次不导入，并找业务负责人或开发者确认。
9. 保存为UTF-8 CSV，文件名包含日期和批次用途，不使用“最终版2”“新建副本”等无法追溯名称。

## 第三步：使用WooCommerce原生导入

1. 进入“商品 → 所有商品”，点击“导入”。
2. 选择本批CSV。
3. **保持“Update existing products”未勾选。** 第一版不得覆盖已有商品。
4. 高级选项不确定时保持默认；不要填写服务器文件路径。
5. 进入字段映射页后逐列核对。SKU、Name、Published、Type、Parent、Regular price、Sale price、Stock、Categories、Attributes、Images和Shipping字段不得凭猜测映射。
6. 出现陌生列、重复列、空映射、错误示例值或无法确认的父子关系时返回，不开始导入。
7. 确认后开始小批量导入，并保留完成页结果截图或证据。

## 第四步：完成页与数据抽查

完成页必须记录：

- Imported
- Imported variations
- Updated
- Skipped
- Failed

第一轮`Updated`必须为`0`。如果不为0，立即停止后续导入，保持页面和文件证据，不继续修正或再次上传。

若某一批因为SKU已存在而出现`Skipped`，先核对是否误用了旧SKU或重复上传；除已批准的D25重复SKU负向测试外，不能把意外Skipped当作正常成功。D25受控复跑同一2行源CSV的结果为Imported 0、Updated 0、Skipped 2、Failed 0，证明更新框未勾选时原生导入器会跳过这两个已存在SKU。

至少抽查：

- 新Simple商品状态为Draft。
- 新商品作者对应实际Website Manager账号。
- SKU、价格、库存、分类、属性和图片符合源CSV；当前批准范围没有父子关系。
- 已有商品的ID、SKU、状态、价格和库存没有变化。
- 未登录访问新父商品精确URL时不可公开。
- 新商品没有进入Product Sitemap、导航或正式内链。

## 第五步：填写商品CSV批次登记

在`CONTENT_ASSET_REGISTER.md`新增一条`D25-CSV-YYYYMMDD-序号`记录，填写：

- 环境、操作账号、日期时间和时区。
- 源CSV文件名、模板版本/指纹、SHA-256、行数和保存位置。
- “仅新增、更新框未勾选、Published=-1”。
- SKU清单或清单位置。
- 导入前商品导出文件和应用备份时间。
- Imported、Variations、Updated、Skipped、Failed。
- 商品字段、作者和匿名公开面抽查结果。
- 异常、停止原因、恢复动作和开发者复核结论。

没有登记的批次不能被视为M3可追溯验收通过。

## 误操作与恢复矩阵

| 问题 | Website Manager先做什么 | 谁恢复 |
|---|---|---|
| 少量错误新建Draft | 停止导入，按批次SKU核对对象，不发布、不永久删除 | Website Manager在复核后移入回收站并登记；开发者抽查 |
| 导入结果出现Updated | 立即停止，不再次上传，不继续编辑受影响商品 | 开发者比较导入前CSV与数据库，决定定点修复或恢复 |
| 商品意外Published | 立即改回Draft，检查匿名URL、Sitemap和缓存并登记 | Website Manager紧急下线；开发者复核公开面和数据 |
| 价格、库存、Variation或Slug大面积异常 | 停止所有批量写入，保留CSV、截图和时间 | 开发者/管理员处理 |
| 文章/Page正文误改 | 使用原生修订恢复受支持正文，再检查状态和非修订字段 | Website Manager可按SOP处理；高风险异常升级开发者 |
| 分类、特色图、Yoast或状态错误 | 不假设会随修订恢复，按对象逐项核对 | Website Manager或开发者按风险处理 |
| 需要数据库/应用恢复 | 不自行进入Cloudways或数据库 | 仅开发者/管理员执行 |

数据库恢复可能覆盖恢复点之后的新商品、文章、订单、媒体和设置，因此不是普通编辑人员的一键撤销按钮。

## 原生记录能证明什么

- 新建商品的`post_author`能证明创建账号，但不能证明来自哪个CSV批次，也不是最后修改人。
- Post/Page的作者和受支持内容字段修订能记录部分修改账号和时间；正文恢复不保证分类、标签、特色图、Yoast、状态和Slug一起恢复。
- WooCommerce导入完成页和用户错误日志可以作为当次证据，但不是永久、完整的活动日志。
- 商品批次登记负责把账号、文件、数量、结果、备份与恢复连接起来。

后台自动活动日志和整批一键回滚属于第二版待选型增强。未完成插件许可证、性能、数据库增长、保留期、隐私和回滚评估前，不安装也不开发。

## 停止条件

出现以下任一情况立即停止批量操作并找开发者：

- `Updated`不为0。
- 任何已有商品价格、库存、SKU、状态、Variation或Slug发生变化。
- 新商品或父商品意外公开。
- CSV列无法确认、映射错位或重复表头。
- SKU重复、Variation父子关系错误或出现未经预期的Skipped/Failed。
- 导入前商品导出或应用备份时间缺失。
- 无法确认商品事实、素材授权或正式发布责任。

## 可复用核心思想

- 跨平台不变量：批量写入前应同时具备数据快照、系统级恢复点、独立操作者身份和批次记录；四者解决的问题不同，不能互相替代。
- WooCommerce/WordPress实现：全局capability可能只是原生工具的入口门槛，并不自动形成业务级最小权限；纯原生方案的限制必须准确标为SOP约束，而不是技术强制。
- WooCommerce/WordPress实现：`post_author`、修订、错误日志和数据库备份各自只覆盖部分证据。审计回答“谁、何时、做了什么”，恢复回答“怎样回到安全状态”，二者必须分别设计。
- Shopify或其他平台对照：同样需要区分产品导出、平台备份/版本记录和批次撤销能力；具体能力与限制必须按目标平台实测，不能把WooCommerce字段或状态值直接套用。
