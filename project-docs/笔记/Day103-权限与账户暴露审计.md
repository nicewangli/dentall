# Day103：权限与账户暴露审计

## 结论与范围

D103 对照总计划“权限和账号审计、编辑/客户越权测试、权限基线完成”开展检查。本轮确认 WordPress 原生 Users REST 会向匿名读者返回已发表 TEST 文章的后台作者显示名、slug 与作者链接；这属于编辑身份暴露，不等于密码、邮箱或后台登录权限泄漏。已在 `dentall-core` 加入经用户授权的定向读取守卫，并在独立隔离 WordPress 验证。它只收紧 Users REST 子面；隔离测试还证实 oEmbed `author_name`/`author_url` 与 RSS2 `dc:creator` 可继续暴露相同显示名，因此 RSK-057 仍为 P2 开放，D103 不标记 Done。

## 功能确认单与授权记录

用户在本轮明确回复“可以，按照你的方案来实施”，授权已提出的最小方案：限制访客和 Customer 对核心 Users REST 列表及非本人数字单项的 GET/HEAD，保留本人资料、内容编辑权限、文章数字作者关联和嵌入机制，并在隔离环境测试。此授权不等于允许修改共享 Local、Staging、Production、第三方核心或真实支付资料。

| 确认项 | 本轮范围与依据 |
|---|---|
| 业务问题 | 公共作者接口直接返回后台编辑身份，扩大针对员工账号的枚举面；需限定可读资料，同时不破坏文章、编辑与客户本人资料。 |
| 角色、频率、来源、数据量 | 读者、Customer、Content Editor、Website Manager、Administrator；读者会访问文章及公开 REST，实际流量未测；来源为 WordPress 原生用户与已发表文章；正式作者数量未核定，以 TEST 作者验证结构。 |
| 第一版必须做 | 访客/Customer 读取 `/wp/v2/users` 集合或员工数字单项时返回 403；本人数字项和 `/me` 仍交由原生身份权限处理；编辑人员既有读能力保持；文章作者数字 ID 与 `_links` 保持。 |
| 第一版明确不做 | 不全局关闭 REST、不删除 `post.author`、不改用户模型、作者 URL 或公开署名策略，不安装插件；oEmbed、Feed、作者归档和历史缓存需另定治理范围。 |
| 候选方案 | 原生后台/角色设置缺少本项目所需的按访客、Customer、本人、编辑者区分的 Users REST 读边界；复用现有 `dentall-core` 的站点级权限生命周期；采用一个最小独立模块及 WordPress 公开 Filter；独立或第三方插件会引入额外更新、权限与回滚面，当前无明确收益。 |
| 数据、权限、安全 | 只读响应拦截，无字段、数据库写入或订单变化；保留前序 `WP_Error`；按角色和本人 ID 检查，防止大小写路由与请求 `id` 覆盖绕过。 |
| URL、SEO、性能、缓存 | 原 URL 不变，受限 GET/HEAD 状态改为 403；文章 `author` 数字 ID 与 `_links` 保留，`?_embed=author` 不返回姓名。Title、Meta、Canonical、Schema、robots、sitemap 未直接改写，真实爬虫、第三方客户端及 Staging 缓存待复验。新增一次 REST 路由/能力判断，未做变更前后性能测量。 |
| 部署与回滚 | 仅当前工作树代码与独立隔离站验证；未部署共享站点。发布需先复核目标版本/备份/缓存，异常时回退 `dentall-core` 0.7.1 的本次守卫变更并复测，不修改核心。 |
| 工时与排期 | 此工作归属 W18 的 D103 权限基线范围；新增守卫、审查和隔离测试有实际工作量，但用户未记录工时，不能虚构小时数。D103 验收未闭环，D104～D108 衔接与 P2 治理时点需在排期复核中确认，不能默认为原计划已吸收。 |

## 最多3项验收结果

1. **已在隔离环境验证：** 访客和 Customer 不能从核心 Users REST 读取员工列表或非本人数字资料，大小写路由与 `id` 覆盖也被拦截。
2. **已在隔离环境验证：** Customer 本人数字项及 `/me`、Content Editor/Website Manager/Administrator 原生读取路径和文章数字作者关联保持可用。
3. **未达到 D103 总验收：** oEmbed/Feed 作者身份出口仍在，目标环境权限、登录防护、日志、缓存与正式内容未完成回归；RSK-057 保持开放。

## 整合分支后续隔离复验（2026-10-08）

在 `e078fc5` 已合成源码的新建 TEST 站复验，环境为 WordPress 7.1、WooCommerce 11.0.0、DentAll Core 0.9.1；该站没有 Yoast、Breeze 或 Varnish。以下结果属于后续证据，不改写上方 Core 0.7.1 源任务的测试计数，也不代表共享 Local 或 Staging 已部署。

| 检查面 | 后续证据与边界 |
|---|---|
| 真实 Customer 会话 | 经 `wp-login.php` 建立 Cookie，并由 `admin-ajax.php?action=rest-nonce`取得 REST Nonce。混合大小写 `GET /wp/v2/UsErS/Me` 返回 200、`id=2`。混合大小写路径的 `POST /Me` 与数字项 `POST /2` 改邮箱均返回 403 `dentall_account_email_locked`；`PATCH` 改密码返回 403 `dentall_account_password_form`；小写 `POST` 对照亦为 403。 |
| 独立复测与数据前后 | 独立复测无 Nonce 的本人 GET 为原生 401，有 Nonce 为 200，改邮箱 POST 为 403。以**登录后、写请求前**为基线，拒绝请求前后的 `WP_User->data` 和 usermeta SHA-256 严格相等；首次登录会生成 session token 并改变 usermeta，因此不能拿登录前快照证明写请求无副作用。 |
| 公开作者出口 | 匿名 oEmbed JSON 为 200，仍返回 TEST 作者名及 `author_url`；RSS2、Atom、RDF 和作者 Feed 均为 200 且含 TEST 后台显示名。TEST Atom 的作者 `<uri>` 也存在并指向此测试站；目标作者个人网址是否有值待查。此站无 Yoast，作者归档为 200；D19 的 Staging 曾在 Yoast 关闭作者归档后实测 301，两个环境的结果不可互相代替。 |
| 缓存与清理 | 本 TEST 站无 Breeze/Varnish，未证明历史 Users REST、oEmbed 或 Feed 响应是否被目标缓存保留。D91 只证实 Staging 的旧公开 HTML 可被 Varnish 保留。TEST 的 HTTP/MySQL 服务已停，20430/20431 端口不再监听；本轮未改运行代码。核对隔离目录位于本工作区且无重解析点后，原生PowerShell递归清理被自动审批以`blocked by policy`拒绝，TEST凭据和数据仍在Git忽略目录，待获准路径处理。 |
| 日志 | TEST `http-error.log` 未匹配 Fatal/Warning；`wp-content/debug.log` 有一条 `wp_update_plugins()` 因测试站 `WP_HTTP_BLOCK_EXTERNAL=true` 无法连接 WordPress.org 的 Warning，不属于本次 REST 守卫运行错误。不能表述为所有日志零错误。 |

这轮新增的 oEmbed/Feed 治理会改变公开输出，原授权明确不包括它们。需按新功能确认单确定团队署名及品牌链接、实际 Feed 格式、客户端、缓存失效、部署和回滚后才能编码；RSK-057 与 D103 总状态继续保持开放。

## 可复用核心思想

- 跨平台不变量：公开署名、后台身份和登录凭据是三种不同事实。收紧一个 API 后必须枚举 HTML、嵌入、Feed、缓存与第三方输出，才能判断整个身份暴露是否关闭。
- WordPress/WooCommerce当前实现：站点级 Users REST 读边界可通过 `rest_request_before_callbacks` 定向拦截；路由大小写、请求参数覆盖与内部嵌入派发必须纳入真实 REST 测试；保留文章作者数字关联和原生权限。
- Shopify或其他平台：同样要核定员工身份、内容作者和公开资料的授权边界；具体 API、主题与 Feed 输出机制需按目标平台官方资料与实测确认，待验证。
