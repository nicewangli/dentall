# 缺少产品经理时，远程独立开发者的业务沟通与边界能力

## 相关笔记

- 后续实践：[[Day9-SKU品牌与属性规则]]

## 结论

DentAll当前采用的方向符合“单人全栈直接对接非技术业务人员”的真实开发场景：开发者提供稳定、可配置、可验证的系统骨架；业务方对商品、分类、价格、库存、图片、文案和事实真实性负责；统一的`DentAll Website Manager`角色让业务负责人可以自行经营内容，而不需要开发者代办日常操作。

这类情况在远程外包、数字游民、跨境企业站和中小企业商城中会很常见。客户通常有行业经验，但没有产品经理，也无法把业务知识直接转换成字段、状态、权限、URL和验收标准。独立开发者真正需要培养的不是“替客户懂完所有业务”，而是把模糊业务安全地转换成系统边界的能力。

需要明确：统一角色不等于共用账号。每位工作人员应使用自己的WordPress账号，再按职责分配同一个`DentAll Website Manager`角色，以保留操作追踪、单独撤权和密码安全。

## 记忆模型：桥梁、骨架、护栏、账本

可以把独立开发者的工作记成四个物件：

1. **桥梁**：把业务人员的自然语言翻译成可实现、可验收的需求。
2. **骨架**：搭建不依赖某批具体内容的通用模型、权限和前端组件。
3. **护栏**：允许业务人员自主工作，同时拦住支付、系统配置、批量删除等高风险动作。
4. **账本**：记录事实、假设、负责人、决策、变更和验收证据。

对应到真实技术工作：桥梁是需求访谈与示例验证；骨架是WordPress/WooCommerce数据模型和动态模板；护栏是capability、nonce、校验、备份及环境隔离；账本是数据字典、ADR、风险登记、变更单和测试记录。

## 最应该培养的八项能力

### 1. 业务分析与追问能力

目标不是学习成牙科产品经理，而是找出系统必须知道的事实。面对一个模糊需求，固定追问：

- 谁使用它？
- 他要完成什么动作？
- 正常流程是什么？
- 有哪些例外、禁止和失败情况？
- 哪份资料是事实来源？
- 谁对内容真实性作最终决定？
- 最晚什么时候必须确认？
- 未确认时能否用`TEST`数据继续验证骨架？

训练重点是用具体样本代替抽象争论。例如不用问“你们的商品模型是什么”，而是让业务方分别解释一个简单商品、一个多规格商品、一个套装和一个询价商品。

### 2. 领域建模与信息架构能力

把客户口中的词拆成：对象、字段、关系、状态和规则。例如在WooCommerce中：

- 商品类别使用Product Categories。
- 可筛选规格使用Global Attributes。
- 影响价格、SKU或库存的选择使用Variations。
- 品牌是品牌，不重复伪装成分类。
- 促销是价格状态或动态集合，不是长期分类。

开发者负责模型能否表达业务，业务方负责具体商品属于哪里、参数是否真实。

### 3. 责任边界与决策权设计

每个重要数据至少明确三件事：谁填写、谁确认、谁承担真实性责任。推荐使用轻量责任矩阵：

| 类型 | 业务方 | 开发者 |
|---|---|---|
| 商品事实、分类归属、价格库存 | 决定并确认 | 提供可录入结构 |
| 字段、权限、动态模板 | 提供使用反馈 | 设计、实现和测试 |
| URL、权限、安全、备份 | 配合确认影响 | 负责技术方案 |
| 支付、物流、税务规则 | 提供正式业务规则 | 按已确认规则实施 |
| 批量导入或迁移 | 提供清洁数据并验收 | 设计映射、预演和回滚 |

没有写明负责人的未知事项，最后通常会默认落到开发者身上，因此责任矩阵应在报价和开工阶段建立。

### 4. 可配置骨架与容错设计能力

系统不能只在当前设计稿和样本数据下正常工作。需要主动覆盖：

- 分类新增、改名、隐藏和清空。
- 缺图、长标题、长分类名和特殊字符。
- 商品无价格、缺货或不可购买。
- 属性项增加、排序变化和合法组合变化。
- 首页只展示精选分类，而不是自动倾倒完整分类树。
- 代码不硬编码业务分类ID、名称和固定数量。

这项能力可以把未来大量内容变化从“开发需求”降级为“编辑操作”。

### 5. 权限治理与风险分级能力

不要在“完全不给权限”和“直接给管理员”之间二选一。更成熟的方法是：

- 按人员职责设计角色，不按后台菜单拆成多个需要切换的账号。
- 每个人使用独立账号，可拥有相同角色；禁止多人共享登录凭据。
- 日常内容操作开放，订单支付、用户、插件、主题、系统设置和部署隔离。
- 批量删除、批量导入、大量Slug变化和数据迁移提高审批与备份等级。
- 先在Local或受保护Staging验证，再开放持续录入。

### 6. 异步沟通与决策压缩能力

数字游民项目很少能靠随时开会推进。每次沟通尽量输出一个“可决策包”：

- 当前结论。
- 已知事实和依据。
- 未知事项。
- 推荐默认方案。
- 备选方案及代价。
- 不回答是否阻塞，以及最晚确认时间。
- 客户只需回复“接受默认方案”或指出修改项。

避免发送宽泛问题，如“你们想怎么做”；改成“材料片和成品护齿会影响商品类型，建议当前按材料片测试，D17前请业务负责人确认”。

### 7. 范围、估时与商业边界能力

合同或项目说明中应区分：

- 包含：需求澄清、代表样本建模、后台骨架、权限、模板、测试和操作说明。
- 不包含：替客户清洗全部历史数据、编写全部商品内容、判断行业参数、持续代建分类、无限会议和无限修改。
- 另行估时：批量数据治理、复杂审批流、第三方系统集成、多语言、多币种、数据迁移及紧急生产支持。

发现新需求时记录原范围、新需求、价值、增加工时、进度影响、风险和是否确认，不能靠个人加班静默吸收。

### 8. 引导式验收与培训能力

非技术人员很难评价系统架构，但能评价自己是否完成工作。验收应让真实用户执行任务：

- 独立创建一个商品和分类。
- 设置价格、库存、图片和属性。
- 创建一篇文章及文章分类。
- 预览、修改、发布或提交审核。
- 故意测试缺图、长名称、错误文件和无权限入口。

开发者观察阻塞点并修骨架，不代替对方完成操作。录屏、短操作手册和错误反馈模板比一次长培训更适合远程协作。

## 可复用的项目流程

### 售前与启动

1. 明确业务目标、用户、核心流程和第一版边界。
2. 要求客户指定一名业务决策人和一名内容负责人；可以是同一人。
3. 收集3～10个代表样本，不等待全部资料齐全。
4. 写明客户负责提供并确认的事实数据。
5. 把“业务梳理/Discovery”计入报价，不作为免费附赠。

### 建模与原型

1. 先区分对象、字段、分类、属性、状态和权限。
2. 用代表样本验证简单、复杂和异常场景。
3. 未确认内容使用明确测试标记，不伪装成正式数据。
4. 只冻结模型和流程，不冻结客户尚未整理完的全部内容。

### 实施与协作

1. 使用Local、Staging和Production分离。
2. 给每位参与者独立账号，按职责分配角色。
3. 每周集中收敛反馈，不让零散消息持续打断开发。
4. P0/P1立即处理；便利性需求进入Backlog。
5. 高影响变更先备份、预演并说明URL、SEO或数据影响。

### 验收与交接

1. 让业务人员独立完成真实任务，而不是只看演示。
2. 验收代表样本、异常状态、导出和恢复路径。
3. 交付权限表、数据字典、操作手册、未决事项和责任清单。
4. 上线后按支持套餐处理新增业务需求，避免无限售后。

## 建议长期维护的七份模板

1. 一页项目范围与成功标准。
2. 业务事实、假设和未知事项清单。
3. 数据字典与代表样本表。
4. 角色权限与责任矩阵。
5. ADR决策记录。
6. 变更申请与工时影响记录。
7. 用户任务式验收清单。

这七份模板比临时记忆更能保护远程开发者，也能降低跨时区沟通成本。

## 需要警惕的客户信号

- 没有人愿意对价格、分类、文案或法律内容作最终确认。
- 所有人都能提需求，但没人能批准范围。
- 要求开发者根据零散资料自行猜测行业事实。
- 一边要求固定报价，一边持续增加内容、流程和集成。
- 拒绝提供代表样本，却要求一次性完成全量导入。
- 要求多人共享管理员账号，或拒绝Staging、备份和验收。

出现这些信号时，应缩小范围、增加Discovery费用、改为按阶段报价，严重时拒绝承接。

## 90天能力训练路线

### 第1个月：会问、会记、会划边界

- 每个需求都练习写“用户—动作—规则—例外—验收”。
- 为现有项目维护假设清单、责任矩阵和决策记录。
- 练习把宽泛问题改写成带推荐默认值的选择题。

### 第2个月：会建模、会做可配置骨架

- 用3～5种代表商品练习分类、属性、变体和状态建模。
- 检查代码中的硬编码业务名称、ID和数量。
- 为缺图、空状态、长文本和权限不足设计统一处理。

### 第3个月：会报价、会验收、会远程交付

- 制作自己的Discovery清单、范围模板和变更单。
- 用任务式脚本组织一次非技术用户验收。
- 把高频操作做成短文档或3～5分钟录屏。
- 复盘实际沟通时间，将业务梳理明确计入下一次报价。

## DentAll带来的可复用经验

- 资料不完整不等于项目整体阻塞；先判断是否足以验证骨架。
- 仓库字段和内部价格不能直接升级为网站正式业务事实。
- D18冻结商品模型和编辑流程，而不是冻结约970条正式内容。
- 统一Website Manager角色解决业务自主权问题；独立账号解决审计与安全问题。
- 首页设计入口、数据库分类树和筛选属性是三种不同概念。
- 开发者最重要的产出不是替客户填满网站，而是让客户能安全地持续经营网站。

## 个人定位建议

未来可以把自己定位为“懂业务建模和交付治理的WordPress/WooCommerce独立开发者”，而不只是接页面和插件开发。核心卖点是：

> 我不要求客户先学会技术，也不会替客户猜测业务；我会用代表样本、责任边界、可配置骨架和分阶段验收，把他们的业务知识安全地转成一个可持续运营的网站。

这个能力组合接近轻量产品经理、业务分析师、解决方案架构师和交付经理，但不代表一个人要无偿承担四份工作。真正专业的表现，是把这些必要工作显式化、模板化、计入范围和报价，并把最终业务责任留给客户。
