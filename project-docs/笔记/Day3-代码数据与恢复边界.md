- 仓库只跟踪项目文档和明确放行的 DentAll 自定义主题/插件代码。
- `wp-config.php`、`.env`、密钥、数据库、uploads、日志、缓存和备份实体均被忽略。
- 自定义代码目录中的 `.env`、`.env.*`、`*.key`、`*.pem` 和 `auth.json` 会在放行规则之后再次排除，避免 Git 规则顺序导致密钥被重新纳入。

## 恢复原则

1. 恢复前先保留故障现场副本，不直接覆盖唯一数据。
2. 数据库先恢复到隔离数据库并验证表数量、关键表和站点 URL，再进入目标环境。
3. uploads 先校验 SHA-256 和压缩包可读性，再解压到隔离目录。
4. 代码优先从远程 Git 恢复；本地 bundle 和工作区 patch 仅作为第二恢复来源。
5. 生产数据可能包含个人信息，正式环境备份必须使用 Cloudways 或另一受控加密位置，不能只保存在开发电脑。

## 可复用核心思想

- Git只管理适合版本化的代码和文档，不是数据库、uploads、运行配置和密钥的万能备份。
- WordPress恢复至少要同时考虑代码、数据库、媒体和环境配置；只备份其中一项不能恢复完整站点。
- “备份文件存在”不等于“可以恢复”。必须在隔离环境解压、导入、检查关键表和站点URL，才算有效证据。
- 校验和用于证明备份在传输或保存后没有损坏；恢复演练用于证明操作路径真正可执行，两者不能互相替代。
- 恢复前先保留故障现场，恢复后再验证，避免一次覆盖把唯一可追查证据破坏掉。
- `.gitignore`应采用最小放行思路：只跟踪明确属于项目的代码，避免宽泛规则意外纳入密钥或第三方文件。
