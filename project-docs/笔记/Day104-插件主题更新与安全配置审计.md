# Day104：插件主题更新与安全配置审计

## 结论与范围

D104 对照总计划中的插件主题更新审计、安全配置和敏感信息检查推进。2026-10-07 的 Staging 盘点记录为 WordPress 7.1.3、WooCommerce 11.0.0、Breeze 2.5.12；10月8日隔离演练的目标为 WooCommerce 11.2.0 与 Breeze 2.6.1。**2026-10-17已重新核官方目标为11.2.1与2.6.2，见下方当前预检**，旧演练不自动覆盖新点版。版本落后本身不能证明 DentAll 已被利用或具备公告中的全部触发条件。全新 TEST 隔离站已完成当时目标的受控升级、数据库迁移、新装冒烟、定向回归和配对恢复；隔离站没有 Staging 的 Breeze 2.5.12 配置，不能复演其原位升级。**共享 Staging、Production 尚未升级，D104 安全基线未验收**。

## 授权与职责边界

用户已同意按本轮方案实施受控升级检查与隔离演练。此授权覆盖隔离副本中的版本更新、必要数据库迁移、定向回归与恢复验证；不把共享 Local、Staging、Production、真实付款、邮件、DNS 或缓存策略纳入自动操作范围。开发者负责版本、依赖、数据库、扩展点与回滚证据；业务人员只在后续目标环境窗口参与内容与核心购物流程验收，不代替技术验证。

## 最多3项验收结果

1. 插件、主题、核心的现有版本、官方更新目标和变更风险均有可核对来源。
2. 独立隔离站完成 WooCommerce 升级与数据库迁移、Breeze 2.6.1 启用冒烟，关键商城、账户、REST 与可观察缓存边界通过定向验证；不把隔离结果外推为 Staging 的 Breeze 原位升级或缓存配置通过。
3. 从升级前同一时点的文件和数据库快照恢复，并记录结果；Staging 的真实插件、主机缓存与发布窗口另行验收。

当前第1项已完成版本与公告核对；第2项中的 Woo 更新组、Breeze 新装生命周期、plain query REST、商品和 Cart 子面已有隔离证据，Checkout 在 TEST 配置下重定向 Cart，账户/PayPal/Yoast 与目标缓存未验；第3项的 TEST 配对恢复通过。D104 的“安全基线完成”仍未达成，RSK-060/P2 保持开放。

## 安全配置与敏感信息

- 当前 Git 跟踪范围排除 `wp-config.php`、数据库、上传媒体、日志与常见凭据文件；本轮仅有范围有限的仓库扫描，不能把“没有命中已扫描模式”写成全历史无泄漏证明。
- Staging 的密码保护、`noindex`、缓存层与访问日志等必须在发布窗口读取实时配置；历史记录不能替代 2026-10-08 的现场结果。数据库快照和文件包可能含账号、配置或 TEST 邮件信息，应限制在隔离目录和受控访问范围内，不进入 Git。
- 升级涉及 WooCommerce 订单、HPOS、Action Scheduler、Cart/Checkout 与 PayPal Sandbox 的兼容面；当前不发真实邮件、不产生真实支付，也不修改正式订单。

3. **分步更新：** 按 [WooCommerce 更新指南](https://woocommerce.com/document/how-to-update-woocommerce/)先更新 Woo 文件、执行数据库更新，再按实际 Action Scheduler 存储读取更新组逐项状态与日志、数据库版本及相对基线的新失败/待办；不运行无关邮件、支付或远程任务。完成后再将 Breeze 从现场旧版原位升级，读回版本握手、整页 HTML 开关、保留的手工排除和最终生成配置；全新 TEST 的默认排除不能代替旧配置迁移。不要同窗口顺手部署尚未合成验收的主题/Core 候选。
4. **目标回归：** 用代表商品/变体、目录筛选与分页、两匿名购物车、Checkout/My Account、账户和 Users REST 核对金额与归属；邮件、PayPal Sandbox 或 TEST 订单仅在对应授权和防外发条件下执行。复核 Yoast Title/OG/Canonical/robots/Sitemap、错误日志，以及 Cloudways Breeze＋Varnish＋对象缓存下的公开页 MISS→HIT、登录/Cart/Checkout/有效 `order-pay`/REST 私有响应、撤稿精确 URL 旧缓存和 RSK-056 规范 Shop 预览开关矩阵。占位页响应不能替代真实交易页验证。
5. **停止与配对回滚：** 数据库迁移或队列不收口、新 Fatal/P0/P1、金额或订单归属异常、受保护响应被缓存时停止放行；先评估快照后订单/内容写入的损失，再按该同点文件与数据库配对恢复，处理相应缓存并复核版本、数据和关键请求。不能只降回旧 Woo PHP，也不能把 D106 的独立恢复副本当作来源应用原位回滚。

A工作包的受控更新准备范围已确认，当前尚未分配共享Staging独占操作窗口。执行前由协调方确认目标应用、锁定的软件版本集合、精确步骤、暂停范围、TEST订单/邮件/支付是否纳入及恢复负责人；功能部署与插件更新分窗，不因另一任务安静就占用。隔离站通过不关闭RSK-060；Production不在本轮范围。

## 可复用核心思想

- 跨平台不变量：依赖更新常改变代码、持久数据与缓存契约。只有同一时点的完整备份、真实迁移结果、关键流程验证和配对恢复，才支撑可回滚的发布判断。
- WordPress/WooCommerce当前实现：WooCommerce 插件版本与数据库版本是两个检查点；Breeze 的 PHP 页面缓存、Cloudways Varnish 和对象缓存是不同层。更新后必须在目标组合中分别检验交易隔离和旧缓存撤销。
- Shopify或其他平台：也需要核对扩展版本、数据迁移、边缘缓存及恢复能力；具体发布和回退机制应查目标平台官方资料并实测，待验证。
