## 先建立整体模型

**一句话模型：** 控制台列出恢复点只是找到“箱号”；只有在独立目标核对内容并安全启动、验证业务状态后，才能证明站点可恢复。

把恢复过程想成搬迁仓库：恢复点是箱号，解开的`public_html`、`private_html`和`mysql`目录是箱内货物清单，目标应用和独立数据库是新仓库；首次PHP请求如同给新仓库通电，可能启动排程和外部连接。这个比喻不能代替文件、SQL、权限、时间点及出站行为的实际检查。

```mermaid
flowchart LR
    A[控制台恢复点] --> B[客服取件报告]
    B -. 待独立核对 .-> C[目标私有目录与SQL]
    C -. 客服报告导入，待独立核验 .-> D[独立文件与数据库]
    D -. 先证明目标专属隔离 .-> E[首次WordPress请求]
    E -. 待D106验证 .-> F[内容、账户与业务状态]
```

主干是“列点→清点→导入→隔离后运行”。图中虚线保留最初核查时的状态；后半段已由Day106实际运行补齐并复用完成Day105，不是当前补做清单。

## 核心概念与职责边界

| 概念 | 准确边界 | DentAll当前判断 |
|---|---|---|
| Cloudways应用备份 | 官方说明覆盖`public_html`、`private_html`和数据库；不自动证明服务器与平台设置已备份 | 逐项核对媒体、`wp-config.php`及环境配置，不能只看345 MB显示值 |
| 同点文件与数据库 | 数据库中的附件、订单及设置必须与对应文件和恢复点时间匹配 | D105静态初核时只核对表名；D106已验代表媒体、版本与订单聚合，仍未做全量逐项一致性核验；不以商品CSV代替整站备份 |
| 入口与出站 | `Application Access OFF`挡住匿名Web入口；Ajith称Cloudways无内置服务器出站HTTP/HTTPS或任意TCP/UDP阻断选项 | 目标临时域名一次匿名GET返回Nginx 503；另建Cloudways服务器本身仍不能证明外发隔离 |
| 恢复职责 | 客服仅获准对新目标暂存和一次离线静态导入；开发者核对证据 | 来源应用不做原位Restore；D106动态验证另设闸门 |

**项目实战代码与Hook/API：D105静态初核阶段不适用。** 此阶段没有新增或修改DentAll运行代码，也没有执行WordPress引导。相关真实入口是Cloudways备份与应用管理界面、目标私有目录及[[../Day105-Cloudways备份现场核查]]；后续D106已另行实施并验证临时环境守卫，不能把D105当时的客服建议写成已完成的D105代码。

## 最初静态阶段的安全、数据与站点影响

- 来源应用未点击Restore、Backup或Clone；本日未修改来源配置、未发送邮件，也未执行备份中的PHP代码。
- 新目标有独立应用和数据库，导入后`Application Access`再次读回OFF，匿名GET得到503。来源与目标库各60张表、表名集合一致，仅核对表结构和估算行数，未查看客户或订单记录。上述结果不证明数据、文件和媒体完整，也不覆盖Master进程、Action Scheduler、SMTP、Webhook、支付或共享Redis。
- 客服截图显示目标`public_html`目录由目标应用用户持有，group=`www-data`、mode=`775`；暂存SQL由Cloudways Master用户持有，group=`www-data`，mode最初为`644`、后续截图为`0600`。拟发送的“只改变目标文件”确认因聊天超时结束而未发出；父目录可穿透性与跨应用可读性未独立验证，不能由mode单独推断外部可访问。
- 恢复内容含TEST客户/订单及SMTP配置；备份和证据不得进入Git或公开日志。目标若缺少可验证的专属出站隔离，保持访问关闭并停止动态验收。
- 支持称同一历史点可人工恢复到另一台新Cloudways服务器，但其平台没有内置出站阻断；单独新服务器不能满足D106首次动态运行闸门。费用只指向通用价格页，无具体最低配置或账单，尚无付费创建授权。
- 本次未修改URL、SEO、缓存、支付、物流或部署策略；后续恢复验证可能涉及这些配置，需分别记录旧值、范围与回滚。

## 动手练习与排错顺序

本日只做已发生的只读观察：核对来源应用、恢复点UTC、目标ID和`Access OFF`，匿名访问目标返回503，并核对两库各60张表的表名集合一致。模板中的“Local最小改动”及故障注入练习不适用，不能为了学习制造数据库写入或首次PHP请求。

1. 若列表有恢复点，先确认时间、来源应用和对应备份类型；`1 Week`与14个可见点不能推出每点的到期日。
2. 若客服报告已取件，先取可核对的目录/SQL清单、字节数、权限和哈希；本次未交付原始ZIP，不能虚构ZIP校验值。
3. 若静态导入报告成功，再独立核对目标库关键表、媒体、配置和来源不变量；在目标专属隔离未证明前不做动态请求。

## 变种应用到其他项目

不同WordPress主题或托管平台仍要区分恢复点、备份内容、独立导入和安全运行；文件目录、后台入口、Cron、邮件、缓存与权限机制应按目标平台重新验证。Shopify的具体备份和恢复机制本日未验证。

## 可复用核心思想

- **跨平台不变量：** 备份存在、内容可读、数据可导入、业务可安全运行是递进证据，后一层不能由前一层推断。
- **WordPress/WooCommerce当前实现：** 文件、数据库、媒体与配置需按同一恢复时点核对；首次PHP请求前要处理WooCommerce计划任务、SMTP、Webhook、支付及共享缓存副作用。
- **Shopify或其他平台：** 保留证据分层原则；对应的导出、恢复及外发控制机制待平台实测，不纳入DentAll第一版实施。
