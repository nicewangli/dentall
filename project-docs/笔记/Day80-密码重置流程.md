# Day80：客户密码重置流程

## 结论

D79候选已由`42fffeb`进入主线，本日据此完成D80 Local候选。第一版只有WooCommerce My Account一个找回入口；存在与不存在账号得到相同公开结果；应用层提供60秒身份冷却；新密码由服务端要求至少12字符。WordPress/WooCommerce继续负责密钥、有效期、单次使用、邮件和成功后登录。

本地合同、回归、真实浏览器和三项独立复核均通过，P0/P1为0。Staging已通过Cloudways Git部署DentAll 0.45.0与DentAll Core 0.5.0，并只向D77受控邮箱真实发送一次密码重置邮件；FluentSMTP与WooCommerce私有日志均记录成功，用户在真实手机邮件客户端打开链接后进入原生新密码表单。Cloudways官方说明真实访客地址位于`HTTP_X_REAL_IP`，目标环境未提供PHP侧可核验证据，因此发布候选移除未经证明安全的`REMOTE_ADDR`来源键，避免共享代理导致全站误伤；来源级保护留给已确认代理拓扑的边缘层。

## 用户确认与范围

- 客户账户邮箱必须由单一客户控制；第一版不存在共享账单邮箱、代理下单或代采购。
- 统一入口：My Account。
- 必须做：通用提示、适度限频、服务端至少12字符。
- 明确不做：CAPTCHA、独立重发按钮、第三方安全插件、自定义令牌、自建邮件队列。
- 已授权Staging建立一个专用TEST客户，向受控测试邮箱真实发送一次，并检查Woo/FluentSMTP私有日志。

## 最多3项验收结果

1. 已知与未知账号公开标题、正文、路径相同，核心找回入口回到My Account。
2. 重复投递受限，11字符拒绝、12字符接受，密钥单次使用且成功后登录正确客户。
3. 五类状态在390、768、1024、1440px可用，无横向溢出、页面/控制台/资源错误。

## 实现边界

### Core职责

`dentall-core/includes/customer-account.php`在Woo默认优先级20之前，以`wp_loaded`优先级19处理有效非空找回提交：

1. 按Woo兼容顺序读取命名Nonce或`_wpnonce`并验证。
2. 将`sanitize_user()`归一化后的身份线索做HMAC，不保存邮箱或用户名明文；不在应用层猜测代理后的来源地址。
3. 先检查全部冷却；任一命中立即返回，不刷新期限、不创建其他键。
4. 未命中时调用Woo原生`retrieve_password()`；随后清理内部Notice并跳转到统一确认页。
5. `validate_password_reset`在写入前执行至少12字符规则。

核心`lostpassword`和`retrievepassword`动作重定向到Woo入口；邮件里已经生成的`rp/resetpass`链接不被拦截。

### 主题职责

子主题不复制Woo模板。`inc/setup.php`只扩大现有账户CSS的条件加载范围；`account-auth.css`复用D79卡片、控件和Focus规则，并增加找回、确认和新密码表单的最小布局。Mobile First使用同一DOM，四端没有复制页面。

## 风险与未验证项

- `WC_Rate_Limiter`是检查后写入，不是原子锁；真正并发的首次请求仍有极小重复邮件窗口，按P3保留。
- 存在账号会生成密钥并同步进入邮件链，公开文案一致不等于恒定时间；Staging观察代表时序，第一版不伪造延迟。
- `REMOTE_ADDR`在代理/CDN后可能是共享地址，任意转发头也不能直接信任；当前因此只保留身份冷却，来源级限频待边缘层具备可信客户端地址时再评估。
- 重复邮箱注册和WAF压力仍待对应阶段；真实SMTP收件、手机邮件客户端打开和目标缓存头已在本轮验证。用户未提交新密码，因此Staging未重复验证12字符保存、成功后登录和链接单次使用，这些边界继续由完全相同代码的隔离Local证据覆盖。

## 可复用核心思想

- 跨平台不变量：公开响应应隐藏账号存在性，但真正安全仍依赖令牌、限频、邮件归属、缓存和日志的共同边界。
- WordPress/WooCommerce当前实现：保留核心重置密钥和Woo邮件链，只在公开入口前补通用反馈、HMAC冷却和服务端长度规则。
- Shopify或其他平台：仍需核对平台原生账户恢复、客户身份、邮件和边缘限频；具体端点、令牌和Hook待验证，不属于DentAll第一版实施范围。
