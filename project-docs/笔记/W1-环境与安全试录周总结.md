## 本周决策

- 第一阶段先交付受保护、禁止索引且无真实支付的Staging后台，不把它表述为正式上线。
- 商品继续使用WooCommerce原生Product，不建立重复商品CPT。
- Git只跟踪项目文档与明确放行的DentAll自定义代码，不跟踪核心、第三方插件、uploads、数据库、日志、缓存、备份实体或真实密钥。
- Staging使用Cloudways Via Git和代码专用部署分支；SFTP只用于排查和应急。
- 低权限Content Editor采用能力白名单，不直接使用权限过大的原生Shop Manager。

## 可复用核心思想

- 第一周最重要的不是快速堆功能，而是建立可重复验证的环境、数据、权限、部署和恢复边界。没有这些边界，后续每次改动都会同时承担数据丢失、秘密泄露和不可回滚风险。
- “网站能打开”“后台能登录”“业务角色能安全完成任务”是三层不同验收。环境健康不能替代对象级权限与真实流程测试。
- 技术代理试录只能证明系统路径存在，不能证明非技术人员理解字段和操作。技术验收与人员验收必须分别命名、分别留证据。
- 备份文件存在不等于可恢复。必须在隔离环境实际恢复并检查数据结构，同时避免用恢复测试污染当前站点。
- `noindex`、密码保护、支付关闭和媒体访问分别控制索引、页面访问、交易与文件公开性，不能相互替代。
- 代码仓库与运行数据应拥有不同生命周期。WordPress/WooCommerce通过Git交付自定义代码，通过数据库和uploads备份保护运行状态；Shopify等托管平台也需要区分主题/应用代码、平台数据和外部资产，只是实现机制不同。
- 最小权限的目标不是让菜单最少，而是让角色完成职责，同时把误操作或账号失陷的影响限制在可恢复范围内。
