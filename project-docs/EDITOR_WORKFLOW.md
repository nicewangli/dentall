# 编辑录入与发布流程

> 当前为开工前v0.2草案。第一阶段为D1～D25约25个工作日；D25综合验收前只录代表样本，不进行全量导入。

## 1. 目标

- 编辑人员可以使用非管理员账号独立录入商品、文章、页面、图片和SEO信息。
- 开发人员可以使用真实内容验证前端，不需要等待所有视觉素材完成。
- 用约25个工作日验证数据、权限、媒体、URL和发布规则，再开放持续批量录入。

## 2. 环境和权限

- 录入环境：受密码保护并设置`noindex`的Staging。
- 禁止在LocalWP和Staging使用真实支付。
- 编辑账号不得安装插件、修改主题、调整固定链接或管理其他管理员。
- Website Manager与SEO人员保留内容级和Yoast高级元数据操作权限；系统不额外阻止已发布Slug、Canonical或robots变更，但这些高影响操作必须先记录原因、目标URL和影响范围，再按变更流程复核。
- 商城管理员权限只授予确需处理订单、优惠券或库存的人。

### D5试录权限基线

- `DentAll Content Editor`只用于D6安全试录：可新建和编辑自己的文章、商品草稿，可上传JPEG、PNG和WebP图片。
- 试录账号不得发布文章或商品，不得编辑他人内容，不得创建页面、管理全局商品分类/属性，也不得访问订单、优惠券、WooCommerce设置、用户、插件、主题或站点设置。
- D11验证后，试录图片单文件上限继续保持5MB，且仅允许JPEG、PNG和WebP；SVG、PDF和其他文件类型继续关闭。后续只有确认公开PDF需求并完成Website Manager最小权限与安全测试后才单独开放；媒体公开URL不得保存敏感资料。
- SEO插件已确定为Yoast SEO Free。Website Manager保留`wpseo_edit_advanced_metadata`，可见内容级SEO与Advanced字段；按用户决定不增加代码限制，Canonical、robots和单页索引调整依靠流程、培训与回归控制。
- WooCommerce原生`Shop manager`权限覆盖订单和商城设置，未确认实际商城管理员前不分配给试录人员。

### 统一业务所有权角色（商品与商城运营权限已完成Local首轮验证）

| 角色 | 业务所有权 | 可独立完成 | 必须升级处理 |
|---|---|---|---|
| `DentAll Website Manager` | 网站业务内容与商城日常运营 | 使用独立账号管理文章、页面、媒体元数据、分类、标签、评论/商品评价、内容级SEO和发布，以及商品、属性项、品牌、价格库存、变体、订单、优惠券、报表、客户创建和WooCommerce日常设置 | 真实支付/退款、批量高影响操作、大量已发布Slug或层级变化、固定链接、全局SEO、插件主题、WordPress用户、数据库和部署按变更流程升级 |
| `DentAll Content Editor` | 被分配的日常录入 | 按既有结构录入草稿和素材 | 新建结构、发布或跨作者修改按负责人流程升级 |
| `Administrator` | 技术骨架与系统管理 | 权限、代码、插件、主题、系统设置、URL机制、备份恢复和部署 | 不替业务方判断商品事实、正式分类归属、价格库存或内容真实性 |

- “业务所有权”表示业务负责人不需要开发者代建每一个商品、分类、文章栏目或标签；开发者只处理技术能力、系统边界、URL影响、安全和异常修复。
- 商品与文章分类均由同一个Website Manager角色日常维护，工作人员无需切换角色，也不需要开发者逐项代建。多人参与时每人使用独立账号并分配该角色，不共享登录凭据。
- Website Manager仍不是Administrator或原生Shop Manager的直接复制：采用项目白名单开放WooCommerce运营能力，不开放`manage_options`、WordPress用户管理、插件、主题、核心更新、数据库和部署。
- 商品、文章、页面、媒体元数据、评论、属性、优惠券、订单入口、客户和报表已在D12完成Local与Staging验证。两名现有网站操作人员都使用该角色并各自持有独立账号；`DentAll Content Editor`保留为未来可选角色，暂不作为当前人员验收要求。
- Website Manager不需要访问WordPress“插件”页面。后续Site Kit由Administrator安装和首次连接，再通过Dashboard Sharing向Website Manager共享只读数据；GTM标签日常管理在Google Tag Manager平台单独授权，WordPress端容器接入和全局追踪配置仍由开发者处理。
- 当前`manage_woocommerce`会开放WooCommerce日常设置能力；这不等于可以无流程修改支付、税费、物流、邮件、Webhook或Production配置。相关操作继续要求变更记录、测试、备份和开发协同。
- Website Manager拥有Yoast高级元数据权限不等于可以无记录修改索引。SEO Title和Meta Description属于日常内容操作；已发布Slug、Canonical、是否索引、nofollow及高级robots属于高影响操作，保存前应记录旧值、新值、原因、受影响URL和复核人。

### 已发布Slug与Canonical操作

1. 草稿或从未公开的TEST对象可在首次正式发布前修正Slug，不为无公开价值的测试URL创建Production重定向。
2. 已发布URL需要修改时，Website Manager先记录旧URL、新URL、原因、页面状态、负责人和回滚方案；记录完成前不保存新Slug。
3. 永久迁移使用一跳301，目标必须是内容和搜索意图一致的200页面；不得把多个不相关商品统一跳首页、商店或分类页。
4. Canonical只用于仍需同时访问的重复或高度相似页面，不用于替代301，也不用于把停售商品权重强行指向不等价商品。
5. 修改后由Website Manager/SEO检查内容与链接，开发者核对状态码、循环/链条、Canonical、robots、Sitemap和缓存；证据写入`URL_SEO_MAP.md`。

### 临时缺货与永久停售操作

1. 临时缺货：Website Manager更新可信库存为0或`outofstock`，保持发布、原Slug/URL、目录可见和禁止Backorders；核对前台显示不可购买。没有确认日期时登记下次复核时间，不把不确定状态当成永久停售。
2. 永久停售：必须先取得业务方确认，记录最后可售日期、售后/资料保留需求、候选替代商品和负责人；不得直接删除、改Slug、复用SKU或只把库存设为0后结束流程。
3. SEO人员评估候选替代是否满足同一产品意图和用户需求，并检查流量、外链、订单支持及内容价值；同分类商品不能自动视为严格替代。
4. 严格替代走301；有持续价值走原URL 200停售页；无替代且无价值走真实404，410仅在有明确永久删除需求时单独评估。
5. Website Manager可以执行已批准的商品内容和库存操作；301、状态码、结构化数据与Production缓存/部署由开发者按变更流程实施和验证。

## 3. 第一阶段开放门槛

| 阶段 | 时间 | 允许操作 | 禁止操作 | 通过标准 |
|---|---:|---|---|---|
| 安全试录 | D1-D6 | 保存1个简单商品和1篇文章草稿 | 批量导入、正式发布、调整系统配置 | 非管理员账号可独立完成且无P0/P1阻塞 |
| 数据原型 | D7-D12 | 建分类、属性和2～3个商品原型 | 全量商品导入、一次性创建大量属性 | 数据来源、字段和媒体规则草案可执行 |
| 商品样本 | D13-D18 | 录入5～10个代表商品 | 推进全量商品、随意增加核心字段 | 简单/变体/促销/缺货/多图等样本通过检查 |
| 内容样本 | D19-D24 | 录入3篇文章和1个页面 | 大量建分类、改变URL结构 | 草稿、预览、审核、媒体和SEO流程通过检查 |
| 综合开放 | D25 | 处理遗留P0/P1并冻结v1规则 | 未验收就批量生产 | 权限、字段、URL、导出、备份和恢复路径通过 |

D6开始试录；D18形成商品模型候选冻结；D24完成文章与页面样本；D25验收后开放批量录入。

### D12最小商品原型

1. 创建一个固定包装的TEST Simple Product，验证唯一SKU、价格/促销、按销售包装计数的库存、Package Quantity及当前`lbs/in`下的TEST物流字段。
2. 创建一个2个Size×2个Shade的TEST Variable Product；只建立3个合法Variations，保留1个非法组合，覆盖Variation SKU、同价/异价、独立库存、缺货、父级物流继承和一个Variation物流覆盖。
3. 只有D12确认需要立即验证`display_only`销售模式和参考价格字段时，才创建第3个TEST Display Only Product；否则留到CR-005实施阶段。
4. 原型名称、SKU、属性值、价格、库存和物流数值都必须明确标记TEST；不借用HP0103G、FG0312D、运动护齿/EVA或锆块的未知正式业务事实。
5. D12只创建原型实际使用的最小属性项；用户已决定保留Local与Staging的TEST对象作为D13及下周回归夹具。它们不得直接转成正式商品，D25开放批量录入前再次决定归档或清理。

## 4. 商品代表样本

第一批5～10个商品至少覆盖：

- 简单商品。
- 可变商品及不同变体价格或库存。
- 正常价和促销价。
- 有货和缺货。
- 单图和多图图库。
- 重量、尺寸或物流信息。
- PDF资料或认证文件（如果第一版确认需要）。

每个样本检查：名称、Slug、SKU、类型、价格、库存、分类、属性、简短描述、详细描述、主图、图库、SEO标题和描述。

### D13简单商品发布字段候选

以下是D13 Website Manager预演后形成的候选，不代表D18商品模型已经冻结：

- 创建草稿即可暂存名称、描述和未齐资料；标准可购买商品发布前必须补齐英文Slug、唯一SKU、正数常规价格、库存状态、至少一个商品分类、简短描述、详细描述、主图及主图Alt。
- 品牌作为DentAll业务发布必填候选：使用`ADS`、经确认的原厂品牌或正式确认的无品牌表达，不使用`Unknown`；品牌归档URL和筛选实现仍按后续计划冻结。
- 启用数量跟踪时必须填写可信库存数量；Backorders默认不允许，例外需要业务确认。没有可信数量时不能填写虚假大数，可按已批准流程仅维护库存状态。
- 促销价格与日期、图库、重量尺寸、属性、GTIN、关联商品、虚拟和下载设置均按商品实际条件填写，不为填满后台而编造。
- WooCommerce技术上允许SKU留空，但DentAll只允许资料未齐的草稿暂时留空。标准Simple、Variable父商品和每个可售Variation正式发布前都必须具备来源明确且全站唯一的SKU；无合适制造商货号时由Website Manager分配DentAll自有SKU。

### D14可变商品操作候选

1. 先确定客户必须选择且会改变SKU、价格、库存、图片或可购买性的属性；只展示或筛选的属性不自动用于Variation。
2. 计算理论组合并取得合法组合表，只创建真实可售组合；D14 TEST矩阵为2个Size×2个Shade，但只保留3个合法Variations。
3. Variable父商品保留系列级唯一SKU，父级价格由可售Variations派生。每个可售Variation分别填写唯一SKU、正数Regular price、库存真相源、Backorders状态及物流继承/覆盖结论。
4. 独立库存模式下，父商品不启用数量库存，由每个Variation维护数量；只有全部Variations确实共享同一物理库存池时才改用父级库存，父子不得同时管理数量。
5. 没有真实默认销售组合时，Size和Shade默认值保持为空。需要默认值时，只能指向合法、启用、有有效价格且可购买的Variation，并在前台验证价格、库存、图片和加购状态。
6. 前台至少验证一个有货组合、一个缺货组合、一个未建立的非法组合及一个异价组合；加购后检查购物车中的属性、数量和金额，并清理TEST会话。
7. 物流字段为空代表继承父值，不等于未知数据已确认；真实物流不同的Variation明确覆盖。D15～D18已验证TEST继承/覆盖机制，正式单位、测量对象和数值仍由业务与后续物流方案确认。

### D15库存与物流操作候选

1. 录入物流前先确认测量对象：产品本体规格进入属性/内容；一个购物车销售单位连同直接包装的发货重量和Length×Width×Height进入Shipping；最终订单外箱不录入单个商品字段。
2. Shipping字段只填纯数值，单位读取当前WooCommerce全站设置。当前Local为`lbs/in`，但承运商、物流插件和真实样本未定，不能复制TEST值作为正式商品数据。
3. Simple在商品自身维护物流数据。Variable各Variation实际相同时可留空继承父值；实际不同时明确覆盖。留空前必须确认父值适用，不能用继承掩盖未知数据。
4. 有可信可售数量时启用数量跟踪；只能确认能否销售时关闭数量跟踪并维护库存状态。两种模式切换后必须保存、重新打开并核对前台，恢复数量模式时显式重填可信数量和Backorders。
5. 第一版默认禁止Backorders。临时缺货时保持已发布商品的URL和Slug稳定，设置`outofstock`并确认前台不可购买；是否全站隐藏缺货商品不得由单个编辑自行决定。
6. 永久停售不直接删除、不自动改Slug，也不把“库存为0”当成完整停售方案。记录业务确认、替代商品、历史流量/外链和订单引用，交给D16决定页面文案、301、Canonical与索引策略。
7. 每次库存测试只操作明确TEST商品，记录ID、SKU和恢复基线；结束时后台重开、WooCommerce CRUD和前台三方确认，购物车清空。不得用该流程创建真实订单或触发支付、税费和正式物流。

### 定制展示商品流程（已确认，待实现验证）

1. 商品继续使用WooCommerce Product和唯一详情URL；编辑仅在业务确认该内容用于展示而非直接销售时启用`display_only`。
2. 编辑可填写经业务确认的参考价格下限和上限；两者是非交易USD展示值，未确认时留空，不得从仓库价格或示例值推测。
3. 前台显示明确标注的参考价格范围，但不显示普通成交价、库存、数量、加购或立即购买，也不进入结账、库存扣减和购买事件。
4. 商品详情提供`Contact Us About This Product`，进入通用联系流程并携带Product ID；Contact页向客户显示当前咨询商品，服务端重新读取商品上下文。
5. Contact提交沿用统一表单记录、邮件、反垃圾、隐私和失败处理，并标记`source=custom_product`；不自动创建报价或WooCommerce订单。
6. 如果未来出现完整报价需求，先将CR-004重新评估为Ready，再实现独立询价记录、权限、人工报价转订单和完整测试。

## 5. 文章与页面代表样本

- 1篇短文章，检查摘要、特色图和列表展示。
- 1篇长文章，检查H2/H3层级、图片和目录需求。
- 1篇包含商品或分类内链的文章。
- 1个固定页面，例如About或政策页。

禁止从Word或其他网站直接粘贴不可控的字体、颜色和内联样式。图片上传前完成文件名、尺寸、压缩、授权和alt检查。

### 5.1 文章作者与审核规则

- 正式文章前台统一公开署名为`DentAll Editorial Team`。Website Manager的后台登录身份和`post_author`继续用于权限、修订和责任追踪，不直接等同于前台署名。
- 两名Website Manager继续使用各自独立账号直接编写、审核和发布，不新增品牌作者账号或新角色，不共享凭据，也不把两人的后台显示名改成相同团队名称。前台模板与SEO输出负责统一品牌署名。
- 第一版文章只承载工厂、公司、产品与服务相关信息，不需要临床专家署名；工厂数据、资质、材料、产能、交付和品牌表述仍须由业务负责人核实。
- 作者归档关闭；文章正文保留可见署名，前端后续优先链接到About或编辑说明页面。
- 标签为可选组织工具，第一版标签归档统一`noindex`。不要为关键词覆盖创建大量近义标签；新增标签前确认它能被多篇文章复用且不与分类重复。
- 分类是第一版博客的主要归档维度。只有正式名称/Slug、包含多篇相关文章并具备独立说明的分类才能作为可索引页面；`Uncategorized`、TEST、空分类和单篇薄弱分类不得进入Production导航或内容验收。
- 如果文章出现临床建议、法规解释、安全操作、诊疗判断或需要专业资质背书的声明，必须停止普通发布流程并升级给业务/合规负责人，重新决定具名作者、审核人和证据要求。

## 6. 发布流程

1. 编辑创建草稿并完成自检。
2. SEO人员检查标题、描述、Slug、内链和图片alt；不替代商品或内容负责人决定业务分类和事实。
3. Website Manager检查分类、事实、价格、版权和品牌表达，并对业务内容作最终决定。
4. 在Staging预览；前端模板未完成时只验内容和字段，不验最终视觉。
5. 获得确认后再发布或进入生产迁移清单。

## 7. 反馈与变更

- 后台无法保存、权限错误、字段缺失或数据丢失：P1，进入当前里程碑处理。
- 影响大量商品或URL的字段变化：暂停批量录入，登记需求变更和迁移方案。
- 纯便利性调整、个性化布局或非必要自动化：P3，进入Backlog。
- 编辑反馈应包含账号角色、内容URL/ID、操作步骤、预期结果、实际结果和截图。
