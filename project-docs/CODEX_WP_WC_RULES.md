# Codex WordPress + WooCommerce 代码与显示规则

## 1. 用途与优先级

本文件用于约束 Codex 在 DentAll 项目中生成、修改和验收 WordPress + WooCommerce 代码。目标是让代码可维护、安全、兼容升级，并在手机、平板和 PC 上稳定显示。

规则优先级如下：

1. 用户在当前任务中的明确要求。
2. 根目录 `AGENTS.md`。
3. 本文件。
4. `project-docs/` 中已确认的需求、架构、数据、SEO 和测试文档。
5. WordPress、WooCommerce 官方编码规范与当前锁定版本的官方 API。

规则冲突、版本未知或需求会改变数据、URL、支付、物流、SEO、缓存、部署时，必须先指出影响，不得静默猜测。

## 2. 编码前规则

- 先检查现有主题、插件、hooks、模板覆盖和资源加载方式，再决定修改位置。
- 先确认任务验收结果、影响页面和适用状态；一次任务最多聚焦 3 个可验收结果。
- 不得假设插件已安装、API 一定存在或版本兼容。版本相关实现必须先查询本地真实版本；需要最新资料时只参考官方文档。
- 优先做最小改动，不顺手格式化、重命名或重构无关文件。
- 发现用户工作区已有改动时必须保留；无法安全合并才请求确认。
- 新增依赖或插件前，说明用途、许可证、性能/升级风险和不引入依赖的替代方案，并更新 `PLUGIN_INVENTORY.md`。

## 3. 代码放置边界

| 类型 | 推荐位置 | 约束 |
|---|---|---|
| 模板、页面结构、样式、响应式 | `app/public/wp-content/themes/dentall/` | 只负责展示，不承载可复用业务规则 |
| WooCommerce 模板覆盖 | 主题的 `woocommerce/` | 最后手段；记录来源版本并在 WooCommerce 升级时复查 |
| hooks、filters、短代码、业务规则 | `app/public/wp-content/plugins/dentall-core/` | 与主题切换解耦；按功能拆文件 |
| 必须始终启用的安全/环境逻辑 | `app/public/wp-content/mu-plugins/` | 保持极小、无 UI 依赖、可审计 |
| ACF 字段 | ACF JSON 或 PHP 注册 | 必须版本化；不得只留在数据库 |
| 密钥和环境配置 | 环境变量或主机密钥系统 | 禁止写进 Git、日志、页面源码或前端脚本 |

禁止修改 WordPress、WooCommerce、父主题或第三方插件核心文件。禁止将正式功能长期放在主题编辑器、Code Snippets、页面构建器的自定义代码区或数据库行内代码中。

## 4. PHP 与 WordPress 规则

### 4.1 基础结构

- 新 PHP 文件使用 `<?php`，纯 PHP 文件不写结束标签。
- 项目函数、类、常量、选项、cron 和脚本句柄统一使用 `dentall_` 或 `DentAll\\` 前缀/命名空间，避免全局冲突。
- 可直接访问的 PHP 文件增加 `defined( 'ABSPATH' ) || exit;`；仅被安全引入且无可执行入口的文件可按结构处理。
- 遵循 WordPress PHP Coding Standards；代码需可读，禁止把完整功能写成超长匿名回调。
- 展示文案使用可翻译函数并采用项目 text domain；包含变量的译文使用占位符，禁止拼接破坏翻译语序。

### 4.2 输入、权限与输出

- `$_GET`、`$_POST`、`$_REQUEST`、REST/AJAX 输入先 `wp_unslash()`，再按字段类型清洗与验证；不得把“清洗后”误当“业务有效”。
- 后台写操作、AJAX 和自定义表单同时检查 capability 与 nonce。nonce 只防 CSRF，不代表用户有权限。
- 输出尽可能延迟转义：文本用 `esc_html()`，属性用 `esc_attr()`，URL 用 `esc_url()`，textarea 用 `esc_textarea()`；受控 HTML 使用最小允许集的 `wp_kses()`/`wp_kses_post()`。
- 重定向优先 `wp_safe_redirect()`；文件上传使用 WordPress API 并验证 MIME、大小、权限和错误状态。
- 不在响应、日志或异常中输出密钥、nonce、密码、完整支付数据或客户敏感信息。

### 4.3 数据与查询

- 优先 WordPress/WooCommerce API；确需 SQL 时使用 `$wpdb->prepare()`，并明确分页、排序和上限。
- `WP_Query`/循环结束后按上下文恢复全局状态；自定义查询必须处理空结果和分页。
- 禁止在模板循环中产生 N+1 查询或逐项外部请求；昂贵结果按数据变化策略缓存，不能盲目永久缓存。
- 数据结构改变需要版本化迁移、备份和回滚路径；不得在普通页面请求中重复执行迁移。

## 5. WooCommerce 专项规则

- 商品使用原生 `product`；分类使用 Product Categories；筛选规格使用全局 Attributes；影响价格或库存的选项使用 Variations。
- 商品、变体、订单、客户、优惠券和库存通过 WooCommerce CRUD/API 读写。禁止直接更新其内部表、订单 `postmeta` 或假设订单一定存储为文章，确保 HPOS 兼容。
- 金额、税费、货币、库存和状态使用 WooCommerce 函数处理；显示价格使用 WooCommerce 已格式化结果，不自行拼货币符号或用浮点数重算金额。
- 购物车、结账、账户和订单逻辑优先 hooks/filters；覆盖模板前必须证明扩展点不足，并在覆盖文件中记录对应 WooCommerce 模板版本。
- 不破坏 WooCommerce 原生表单字段名、nonce、notice、variation、AJAX fragment 和可访问性属性。
- 购物车、结账、账户、登录态和个性化价格页面不得使用会串用户数据的整页缓存。
- 新功能按适用范围验证：简单商品、变体商品、促销、缺货、隐藏、免税/含税、优惠券、运费、匿名/登录用户、支付成功/失败/重复回调。
- 未经明确确认，不启用真实支付、不修改真实订单或客户数据、不触发真实邮件/短信。

## 6. CSS、HTML 与稳定显示规则

### 6.1 禁止散落的行内代码

- 默认禁止 PHP/HTML 模板中的 `<style>`、`style=""`、`<script>`、`onclick` 等行内事件属性。
- CSS 和 JS 必须放入主题/插件的独立文件，通过 `wp_enqueue_style()`、`wp_enqueue_script()` 加载，并使用文件版本或构建产物版本进行缓存失效。
- 只有运行时动态值无法用 class、data attribute、CSS custom property 或本地化脚本安全表达时，才允许 `wp_add_inline_style()` 或 `wp_add_inline_script()`；必须保持很小、转义数据并在代码注释中说明原因。
- 禁止从 CDN 临时加载未登记的库；第三方资源必须说明隐私、SRI/CSP、性能、许可证和不可用时的降级策略。

### 6.2 CSS 组织

- 移动优先，从基础样式向较宽断点增强；断点依据内容布局，不为某一台设备硬编码。
- 使用项目设计 token 管理颜色、字体、容器、间距、圆角、阴影和层级，禁止同类数值在页面中反复散落。
- 项目组件 class 使用 `dentall-` 前缀或已确认的组件命名法；选择器保持低特异性，避免 ID 选择器和深层嵌套。
- 不使用 `!important` 解决普通层叠问题；若为覆盖第三方样式确实需要，必须限定作用域并写明原因。
- 不用固定高度承载可变文案；优先使用 `min-height`、自然流、Grid/Flex 和 `clamp()`。布局必须承受中文/英文长标题、价格、促销标签和缺失内容。
- 不通过 CSS 隐藏关键购买信息来“修复”小屏；信息取舍必须有产品决定。
- 避免依赖易变的 WooCommerce 内部 DOM 层级；覆盖 WooCommerce 样式时限定到项目容器，防止影响后台或其他页面。

### 6.3 HTML、图片与状态

- 使用语义化 HTML；一个页面保持合理标题层级。按钮执行动作，链接负责导航，不用 `div` 模拟交互控件。
- 表单控件必须有可见 label；必填、帮助、错误信息通过文本表达并与字段程序化关联。
- 图片使用 WordPress 图片 API 和合适尺寸，保留 `srcset`/`sizes`；内容图提供有意义的 alt，装饰图使用空 alt。
- 图片声明 `width`/`height` 或稳定 `aspect-ratio`，并设置合理 `object-fit`，防止 CLS、拉伸和商品卡跳动。
- 组件至少考虑适用的正常、hover、focus、active、disabled、loading、empty、error、success、缺图、长文本、售罄和不可购买状态。
- DOM 中的 ID 必须唯一；重复组件不得生成重复 ID。

### 6.4 响应式与无障碍基线

每次前端修改至少验证以下视口，允许在其附近抽查：

| 视口 | 重点 |
|---|---|
| 390px | 单列、菜单、筛选、表单、触控、无横向滚动 |
| 768px | 平板竖屏、两列切换、弹层和键盘 |
| 1024px | 平板横屏、导航、商品网格、侧栏 |
| 1440px | 容器上限、留白、网格密度和大图清晰度 |

同时遵守：

- 320px 以上不得出现非设计要求的页面级横向滚动。
- 键盘可完成导航、菜单、筛选、加入购物车、购物车、结账和账户关键流程。
- 保留清晰的 `:focus-visible`，弹层正确管理焦点并支持 Escape 关闭；关闭后焦点返回触发元素。
- 触控目标建议至少 44×44 CSS px；颜色对比达到 WCAG 2.2 AA，不以颜色作为唯一状态提示。
- 尊重 `prefers-reduced-motion`；动画不阻塞操作，不用无限动画表达普通状态。
- 屏幕阅读器可获知 AJAX 更新、购物车变化、字段错误和加载结果，必要时使用合适的 live region。

## 7. JavaScript 规则

- 新功能优先使用小型、无全局污染的原生 JavaScript；只有 WooCommerce 现有事件链或项目既有依赖明确需要时才使用 jQuery。
- 通过 WordPress enqueue 依赖声明控制加载顺序；脚本放页尾或使用合适加载策略，不能阻塞首屏。
- PHP 数据通过受控配置对象、data attribute 或 WordPress 脚本接口传入；禁止字符串拼接可执行 JavaScript。
- 所有 DOM 查询处理元素不存在的情况；组件重复出现时逐实例初始化，避免重复绑定事件。
- AJAX/REST 请求验证 nonce、权限和参数；处理超时、取消、失败、重复点击和服务器返回异常，不只写成功路径。
- 不将客户端校验当作唯一校验；价格、库存、权限和订单状态必须由服务端再次验证。
- 控制台不得残留调试日志、未处理 Promise rejection 或第三方报错。

## 8. SEO、性能与缓存

- 不为视觉调整随意改变 URL、标题层级、Canonical、Schema、面包屑或可索引内容；需要改变时先更新 `URL_SEO_MAP.md`。
- 不重复输出 WooCommerce/SEO 插件已经提供的 Product、Breadcrumb 或 Organization Schema。
- 页面模板返回正确 HTTP 状态；空搜索、无商品和 404 不得统一伪装为 200。
- 避免首屏大图、未压缩素材、同步第三方请求和整库查询；图片使用合适格式和尺寸，非首屏资源按风险延迟加载。
- 缓存 key 必须包含会改变输出的语言、币种、用户状态、查询参数等维度，并有明确失效条件。
- 交易流程不得依赖前端缓存数据作为价格、库存或权限事实。

## 9. Codex 每次交付格式

Codex 完成代码任务时必须明确给出：

1. 结果：实现了什么，可在哪个页面/流程看到。
2. 文件：新增或修改的文件列表及职责。
3. 验证：实际运行的静态检查、自动测试、页面/视口和业务场景；不得把“建议运行”写成“已通过”。
4. 影响：数据、URL/SEO、缓存、支付、物流、邮件、权限、部署和 WooCommerce 升级兼容性。
5. 遗留：尚未验证、依赖素材/账号/配置的项目及风险。

禁止只返回大段代码而不说明放置位置、调用入口、资源加载方式和验证结果。禁止在没有运行证据时使用“已完全兼容”“已修复所有问题”之类结论。

## 10. 最低完成清单

### 通用

- [ ] 变更只覆盖已授权范围，未修改核心或无关文件。
- [ ] PHP 语法/静态检查通过；无明显警告、notice 和敏感调试输出。
- [ ] 输入清洗验证、权限、nonce、输出转义和 SQL 预处理已按上下文检查。
- [ ] 正常、空、错误和边界状态已按适用范围验证。
- [ ] 修改文件、验证证据和未验证项已记录。

### 前端显示

- [ ] 390、768、1024、1440px 已检查，320px 以上无意外横向滚动。
- [ ] 缺图、长标题、长价格/促销文案、售罄和不可购买状态未破坏布局。
- [ ] 键盘、focus、label、错误提示、对比度和动态通知已检查。
- [ ] 页面无明显 CLS、图片拉伸、闪烁、控制台错误和重复 ID。

### WooCommerce

- [ ] 未直接读写订单/商品内部存储，HPOS 兼容路径明确。
- [ ] 商品、变体、价格、库存、购物车、优惠券、运费、结账和账户中受影响的流程已回归。
- [ ] 匿名/登录、成功/失败、重复提交或回调等适用状态已覆盖。
- [ ] 缓存未污染购物车、结账、账户和登录态。
